# case 9 — the laptop's shields are down (sharp, fails safe)

## .narrative

the commander once ran `sudo tailscale set --shields-up=false` to test a local service from a
grove, and forgot it. his laptop now accepts inbound tailnet traffic, and every service it listens
on is open to every camp grove. the next tree apply says so: verify ✋s that this laptop accepts
inbound traffic, and the upsert has already put the shields back up. had the daemon refused the set,
the run would 💥 rather than claim shields up. when the daemon's prefs cannot be read at all, verify
💥s — an unread shield is never reported as up.

## .timeline

```
given a joined laptop (`local@unix`, a member, a camp peer), shields down
  when [t0] the commander runs `sudo -v && rhx grove.provision --what 5.23.tailscale --mode apply`
    then configure.upsert `this node already joined the tailnet — no join owed`               # B5 (C5)
     and it sets shields up: `tailscale set --shields-up`, bounded at 10s                    # B17
     and it rereads the prefs, and prints `shields up — inbound tailnet traffic now refused ✔`
     and configure.verify ✔ joined as a member · no tags · shields up · a camp grove is a peer
  when [t1] the daemon ignores the set
    then configure.upsert 💥 shields-up was set, but the daemon does not report it          # B17
     and it names the hand check: tailscale debug prefs | jq .ShieldsUp
  when [t2] a verify runs while the shields are still down (a plan, or an agent seat)
    then configure.verify ✋ this laptop accepts inbound tailnet traffic (shields down)       # B17
     and it names the one line to rerun
  when [t3] the daemon's prefs cannot be read
    then configure.verify 💥 could not read whether this laptop's shields are up
```

## .fail-safe

fast (the upsert repairs it on the first apply), loud (a ✋ on every verify while down; a 💥 where
the set does not take), teaches the fix (the rerun line). an unread shield is a 💥, never a ✔ —
the one failure that would hide an open laptop.
