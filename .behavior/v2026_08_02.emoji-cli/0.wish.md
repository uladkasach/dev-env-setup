wish =

lets build an emoji cli. an emoji search thing.

why? because there's no fast way to get an emoji into what im typing today.

---

## most important

**tab autocomplete.**

thats the whole point. i want to type a few letters and tab straight into the
emoji, inline, wherever my cursor already is. no popup, no context switch, no
copy-paste round trip.

everything else is secondary to that.

## and also

- **aliases** — short names i can tab against, plus my own custom ones
  (the vibe set: 🐢 🌊 ✋ 💥 etc). i should be able to add my own without
  a rebuild.
- **search** — when i dont know the name, let me browse/fuzzy find
- keyword search, not just unicode names. "happy" should find 😀.
  kitty's builtin picker cant do this — its names-only, so you have to
  already know its called "grinning face". thats the gap.

## constraints

- **fast.** this sits in the keystroke path. no interpreter boot in the hot
  path. if it feels laggy its useless.
- works in kitty + tmux + zsh, which is where i live
- repo is the source of truth — install procedure, not a one-off

---

## open question

"aliases" is doing two jobs above and i havent decided which matters more:

1. shell aliases — short commands (`e`, `em`) to invoke the thing
2. emoji aliases — custom keyword → emoji mappings i can extend

leaning 2, since thats what makes tab useful. but maybe both, theyre cheap.

## notes from the lookaround

- kitty already ships `kitten unicode-input` on ctrl+shift+u — but its index
  is built from unicode NAMES only. no CLDR keywords. and its emoji tab is
  hardcoded to 80 chars (U+1F600–1F64F), so 🚀 🎉 🔥 arent even in it.
  verified in kitty source, not guessed.
- `uni` (go, static binary) does real CLDR keyword search and prints to
  stdout — the lower-effort alternative if diy turns out to be a slog
- CLDR annotations json is the good dataset (438kb, gives 😀 → cheerful,
  grin, happy, laugh, smile, teeth)
- `kitten clipboard` covers clipboard without wl-copy, and tmux.conf already
  has allow-passthrough + set-clipboard on
- fzf + a precomputed TSV is likely the fastest shape: no python, no node,
  only fzf itself in the hot path

speed ranking above is architectural inference — nobody benchmarked it yet.
worth measuring before committing.
