# case=5 — super+v on a grove whose tmux.conf predates the selector

holder `tmux.remote` · far conf `stale` · sharp · alterpath (chosen for a demo: it is the densest sharp path)

## .narrative

the human presses super+v in a duct on a grove not yet provisioned with this tmux.conf. kitty sees `in_tmux` and sends tmux its key, `CSI 9999 ~`. the far tmux has no bind for it, so it forwards the bytes to the pane. a shell prompt shows a stray `~`; an nvim or a claude prompt receives an unknown key.

no state breaks and no data is lost. but the human gets no hint of the fix either: they see a dead key and a tilde.

## .why it stays an alterpath

care = freq × cost. freq is high only until each grove's next provision of 2.8.tmux, then zero. cost is one stray character, with no data loss and no signal sent. so the total is low, and it decays to zero on its own.

## .what makes it fail safe

- the bytes are a private sequence that no key on any keyboard produces, so they cannot trigger an app's own bind by accident
- the cure is one entrypoint call on that grove, named in the vision's assumptions

## .timeline

```
given a grove duct whose tmux.conf has no user-keys[0]
  when [t0] super+v
    then the far tmux does not enter copy-mode
    then the pane receives CSI 9999 ~ (a shell shows `~`)
  when [t1] rhx grove.provision --what 2.8.tmux --mode apply, on that grove
    then the far tmux holds the binds
  when [t2] super+v
    then copy-mode opens, as in case=3
```
