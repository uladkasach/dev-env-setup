# case=6 — the copy stops short of the desktop clipboard

the sharp twin of every copy cell · sharp · critipath (every copy crosses this seam)

## .the seam, per holder

a copy is worth naught until it reaches the desktop.

| holder | hop | what carries it | what would cut it |
|---|---|---|---|
| tmux | tmux → kitty | an OSC 52 write, which tmux emits only for a client whose terminal has the `clipboard` feature | `terminal-features 'xterm-kitty:clipboard'` absent from tmux.conf, or a client attached before it was set |
| tmux | kitty → desktop | kitty accepts the write when `clipboard_control` includes `write-clipboard` (its default) | a kitty.conf line that narrows `clipboard_control` |
| overlay | nvim → desktop | nvim's `+` register, through its clipboard provider (`wl-copy` on this desktop) | no provider on the box: wl-clipboard removed, or a session with no display |

## .how each cut fails loud

- **tmux → kitty:** 2.8.tmux's verify checks every attached client for the declared features, `clipboard` among them, and fails provision with the fix
- **kitty → desktop:** 4.3.2.emulator's verify reads `clipboard_control` through kitty's own loader and fails provision if `write-clipboard` is absent, with the fix
- **nvim → desktop:** nvim itself fails at the moment of the copy: `"+y` with no provider prints `clipboard: No provider. Try ":checkhealth"`, which names the fix. init.lua's "copied to clipboard" toast is gated on a provider, so it never contradicts that error

the tmux hops are config, so they cannot fail per copy — only regress, and a regression is caught at provision. the nvim hop depends on a live provider, so it is caught at the copy itself.

## .narrative

**the tmux half.** months later, a kitty.conf change narrows `clipboard_control` for a reason unrelated to this selector. the human runs `rhx grove.provision --mode plan`, as they do after any pull, and reads one red line: kitty's clipboard_control lacks write-clipboard, so a tmux copy never reaches the desktop, and here is the fix. they apply it before they ever meet the silent version — a paste that yields the old clipboard.

**the overlay half.** on a box where wl-clipboard was removed, the human opens the overlay, selects three lines, and presses ctrl+c. there is no "copied" toast. instead nvim's message line says there is no clipboard provider, and to run `:checkhealth`. they know at once the copy did not leave, and why.

## .timeline

```
given kitty.conf narrows clipboard_control, without write-clipboard
  when [t0] rhx grove.provision --what 4.3.2.emulator --mode plan
    then the verify fails: "kitty's clipboard_control lacks write-clipboard"
    then it names the effect: a tmux copy never reaches the desktop, silently
    then it names the fix
given tmux.conf no longer asserts the clipboard feature for xterm-kitty
  when [t1] rhx grove.provision --what 2.8.tmux --mode plan
    then the verify fails on the attached clients that lack the declared feature
given the box has no clipboard provider, and the overlay is open with a selection
  when [t2] ctrl+c
    then nvim reports "clipboard: No provider", and names :checkhealth
    then no "copied to clipboard" toast fires
given every hop converged
  when [t3] super+v, enter, ctrl+c — in either holder
    then the copy reaches the desktop (case=1, case=2)
```
