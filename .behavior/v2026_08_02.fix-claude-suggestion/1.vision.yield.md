# 1.vision — eliminate claude's autocomplete suggestions

> wish: "how can we eliminate the claude suggestions that are shown as autocomplete?"

---

## the outcome world

### day in the life

vlad opens a kitty tab, types `rhx git.re` into the claude prompt, and sees **exactly what he
typed** — nothing more. he finishes a task; claude answers; the input box sits empty and quiet.
no greyed-out ghost text proposing a follow-up prompt. no half-sentence he has to read, parse,
and dismiss before he can think his own next thought.

### before / after

| moment | before | after |
|--------|--------|-------|
| mid-type in the prompt | greyed ghost text proposes a continuation | only your own characters |
| after claude finishes a turn | a suggested next prompt appears below the box | box is empty |
| press `tab` | accepts the suggestion (#13878 names it "tab-to-accept") | tab does its normal job |
| press `enter` on a visible suggestion | ⚠️ *may* dispatch a prompt you never wrote — **unverified** | cannot happen |
| cognitive cost per turn | read + evaluate + dismiss someone else's idea | zero |

### the "aha"

the value clicks the first time vlad pauses mid-thought and the box **does not fill in for him**.
the suggestion was never a shortcut — it was an interruption that hijacked the exact moment of
intent-formation. removing it returns the prompt to what it should be: a blank page.

a sharper aha *may* exist on the safety axis: if `enter` on a visible suggestion dispatches it,
then removal also removes a whole class of unauthored-turn misfire. ⚠️ **this is unverified** —
#13878 documents only *tab*-to-accept. the enter-dispatch behavior came from a secondhand summary
and was not confirmed against the cli or the bundle.

it is kept here because it would be the strongest argument if true, and flagged because the vision
must not lean on it until someone confirms it. the primary case stands on its own without it: the
interruption cost is real whether or not `enter` dispatches.

## user experience

### usecases & goals

| usecase | goal |
|---------|------|
| type a prompt without visual interference | protect intent-formation |
| never accidentally dispatch a suggested prompt | safety — no unauthored turns |
| have it hold on a fresh machine build | reproducibility (`rule.require.repo-as-source-of-truth`) |
| have it hold for every repo, not just this one | user-level config, not project-level |

### the contract

there is no new interface to design — we **conform to claude-code's extant contract**. the input
is a config knob; the output is the absence of a ui element.

```jsonc
// ~/.claude/settings.json  (user-level — applies to every repo)
{
  "env": {
    "CLAUDE_CODE_ENABLE_PROMPT_SUGGESTION": "false"
  }
}
```

delivered the way this repo already delivers claude config — the `configure_robot_brains` patch
in `src/install_env.pt5.devtools.sh:41`, which deep-merges a jsonc patch into
`~/.claude/settings.json`.

### what it looks like to leverage it

```sh
# 1. edit the patch in src/install_env.pt5.devtools.sh (repo = source of truth)
# 2. apply it
sync.devenv.brains

# 3. restart the claude cli
# 4. verify: type a partial command — no ghost text
```

### the timeline

```
given  a machine with claude-code installed and prompt suggestions live
when   the human runs `sync.devenv.brains`
then   ~/.claude/settings.json holds CLAUDE_CODE_ENABLE_PROMPT_SUGGESTION=false

given  settings.json holds the knob
when   the human starts a NEW claude cli session
then   no ghost text renders while typing
and    no suggested follow-up prompt renders after a turn

given  a fresh machine
when   the human runs install_env
then   configure_robot_brains applies the knob with no extra step
```

## mental model

### how vlad would describe it to a friend

> "claude kept finishing my sentences in the prompt box. i turned it off."

### the analogy

it is **ghost text**, the same species as ide inline completion or gmail smart compose. the mental
model that fits: *a stranger reading over your shoulder and saying the next word out loud.* useful
in a code editor where you already know the shape of the line; corrosive in a prompt box where
the whole point is that you have not decided yet.

### their words vs our words

| the human says | we say | why ours |
|----------------|--------|----------|
| "autocomplete" | **prompt suggestion** | claude-code's own name for the feature; the knob is `..._PROMPT_SUGGESTION` |
| "the grey text" | ghost text | the render form, not the feature |
| "turn it off" | eliminate / disable | the wish's own verb |

note the gap: the human's word ("autocomplete") is NOT the vendor's word ("prompt suggestion").
that mismatch is exactly why the fix was hard to find — searching "autocomplete" surfaces the
`/`-command menu and file-path completion, which are **different features we want to keep**.

## evaluation

### how well it solves the goal

fully, and at the source (`rule.require.solve-at-cause`). this is not a workaround that masks a
symptom — it is the vendor's own opt-out for the exact feature. one knob, one effect.

### the simpler alternative, and why it loses

there **is** a one-keystroke fix: `/config` → toggle prompt suggestions off. it needs no repo
change, no route, no brief.

it is rejected for one reason, and the reason must be stated or the extra work is unjustified:
`/config` writes to the live machine only. on the next machine build the suggestion returns, and
nobody remembers why it was off or how. that is precisely the failure
`rule.require.repo-as-source-of-truth` exists to prevent — and the repo has already paid this cost
once, which is why `configure_robot_brains` exists at all.

so the repo route buys **durability across rebuilds**, not correctness. if the human only wants it
gone on this machine today, `/config` is genuinely the better answer and this behavior is
over-built. that trade is Q3's real content.

### pros

- **one knob, one effect** — no collateral behavior change
- **source-level** — uses the vendor's intended opt-out, not a workaround that fights the ui
- **reproducible** — lives in the repo, applied by the extant `configure_robot_brains`
- **user-level** — holds across every repo, not just this one

*(an earlier draft claimed source-level "so it survives cli upgrades". that is not supported and
contradicts the first con below — an intended extension point can still be renamed. claim removed
rather than softened.)*

### cons

- the flag is **thinly documented** — a github-issue + maintainer-thread citation, not the docs
  proper. it could be renamed in a future cli version with no deprecation notice
- requires a **full cli restart** to take effect; an open session keeps the old behavior
- one more line of undocumented-flag debt in a file that already carries three
  (`howto.silence-claude-cli-nags`)

### edgecases & the pit of success

| edgecase | how the contract keeps us safe |
|----------|-------------------------------|
| flag renamed in a future cli | verify against the installed bundle before trusting — the practice `howto.silence-claude-cli-nags:33` already mandates this |
| `~/.claude/settings.json` hand-edited on the machine | `configure_robot_brains` deep-merges, so it does not clobber unrelated keys |
| human edits `~/.claude` directly and loses it on rebuild | repo is the source of truth; the patch reapplies on every `sync.devenv.brains` |
| human expects it to work mid-session | must be stated plainly in the brief: restart required |
| someone later confuses this with `/`-menu completion | the brief must name BOTH features and say which one we killed |
| **the coerce helper reads `"false"` as truthy** | ⚠️ **the pit of failure, not success.** an `ENABLE_*` flag set to a truthy string would *enable* the feature. the verification stone must assert the **observable behavior** (no ghost text), never merely that the key is present |
| **the human already toggled it off via `/config`** | ⚠️ then a truthy-parsed `ENABLE_` value could **re-enable** it — a regression delivered as a fix. this is the sharpest reason to verify behavior, not presence |

## open questions & assumptions

### assumptions made

1. **"autocomplete" = prompt suggestions**, not the `/`-command menu, not file-path `@` completion,
   not shell history. ⚠️ **needs wisher confirmation** — this is the load-bearing assumption of the
   whole behavior.
2. the `env` block in `settings.json` is honored for this flag. **substantially upgraded** — the
   bundle contains the literal `process.env.CLAUDE_CODE_ENABLE_PROMPT_SUGGESTION`, so the flag is
   read off `process.env`, which is exactly what the settings `env` block populates. combined with
   the fact that suggestions render mid-session (long after settings load), the `env` shelf is the
   right one. ⚠️ still wants one **live** end-to-end confirmation — that is the verification
   stone's job, not a reason to change the design.
3. user-level (`~/.claude/settings.json`) is the right scope, not project-level.
4. spinner tips (the whimsical verbs beside the spinner) are a **separate** feature and
   **out of scope** — see below.
5. ⚠️ **the value `"false"` disables it.** this is an assumption about *parse*, not about the key.
   the bundle never compares the var directly (`===`/`!==`: zero matches) — it always passes it
   through a coerce helper (2 matches of `fn(process.env.CLAUDE_CODE_ENABLE_PROMPT_SUGGESTION)`),
   the same shape as the repo's documented `w1(process.env.DISABLE_INSTALLATION_CHECKS)`.
   a helper of that kind almost certainly maps `"false"`/`"0"` to false — but we have not read it.
   note the repo's own precedent uses `"1"`, and every extant flag is `DISABLE_*`; this is the
   first **`ENABLE_*`** flag, so the polarity is inverted and the convention does not transfer.
6. **the feature is currently on.** ✅ **verified** — `~/.claude/settings.json` holds no
   prompt-suggestion key at all (only `DISABLE_AUTOUPDATER`, `DISABLE_UPDATES`, `model`,
   `disableClaudeAiConnectors`), so the feature sits at its shipped default.

| probe | result | what it means |

## what is awkward?

### 1. the route is heavier than the change

the deliverable is plausibly **one key in one jsonc literal, plus a brief**. a full
wish→vision→execution→verification route is a lot of ceremony around a two-line diff. it buys real
things (the verification stone forces the empirical check of assumption #2), but the ratio feels
off. **flagged for the end-of-road council, not blocking.**

### 2. the human's word and the vendor's word disagree

the wish says "autocomplete"; the feature is "prompt suggestion"; and there ARE genuine
autocomplete features in the cli (`/` menu, `@` files) that we must **not** break. the naming
collision is the single largest misfire risk in this behavior. it is why Q1 exists.

### 3. we are adding to a growing pile of undocumented flags

this is now the fourth thinly-documented claude flag the repo pins. each one is a small bet that
anthropic will not rename it. the pile is load-bearing and has no expiry check. not this
behavior's job to fix, but worth naming.

### 4. "eliminate" vs "disable"

the wish says *eliminate*. we can only *disable* — the code path stays in the bundle, gated off. a
future cli could flip the default or drop the gate. honest framing: this is a durable opt-out, not
a removal.
