# case=3 — a backup or restore that cannot run says so, and names who fixes it

critipath · sharp · cells b1–b5, b13, b20, o2, o3, o5, o6, o7, l3, l4, r16 · sketch, not proof

## .narrative

the dangerous backup is the one that quietly stopped. a hetzner grove whose aws identity was never
applied, or a grove whose bucket name was never declared, would run every hour and put naught —
and a commander who saw no error would believe his work was safe.

so the agent never guesses. each hour it fails loud: the journal, the status file, and every plan
on the box carry `✗ FAILED` with the cause and the one fix. a grove whose last good run is older
than two hours reads `✗ STALE`, whatever the reason. and the commander sees it where he already
looks — `rhx git.grove.stats` from his laptop — without a duct to the box.

the same rule holds on the way back. a restore or a list that cannot reach the bucket says so; it
never prints an empty list a commander would read as "this grove left naught".

## .timeline

```
given an enrolled grove
when [t0] the last ok run is 3h old                                              # o3
  then the bundle verify prints
    ✗ grove backup · STALE · last ok 3h ago
       └─ journalctl -u grove-backup --since -3h
when [t1] the default aws credential chain answers naught (hetzner, roles anywhere not applied)   # b3, o2
  then no unit packs, status.json reads { verdict: failed, cause: "no aws credential" }
  and the verify prints
    ✗ grove backup · FAILED · no aws credential
       └─ owed by ahbode/infrastructure: the grove's roles-anywhere identity (infra#64, part 3)
when [t1.ec2] an ec2 grove's credential answers, but the put is denied            # b4
  then the run fails with cause "access denied: s3:PutObject", and the fix names infra#63's grant
when [t2] /etc/grove/name or the bucket declaration is absent                     # b1, b2, o2
  then the same shape, with cause "grove name undeclared" or "bucket name undeclared"
  and the fix names the infra declaration owed — never a value to type
when [t2.both] a fresh hetzner grove lacks both its bucket declaration AND its aws identity   # b5
  then the run checks reach in its written order (grove name → bucket name → credential)
  and stops at the first absent one; it never probes the credential with no bucket to aim it at
    ✗ grove backup · FAILED · bucket name undeclared
       └─ owed by ahbode/infrastructure: the bucket name, declared on the box (owed item 1)
  and once infra declares the bucket, the next hour's run reports the next cause, `no aws credential`
  and the verdict is ✗ at every step until the last cause is cured — never a ✓ over a gap
when [t2.stats] the commander runs `rhx git.grove.stats --box grove-1` from his laptop (infra's skill)   # o6
  then among its rows reads the same line, from status.json over ssm
    backup: ✗ FAILED · no aws credential · 3h
when [t2.probe] the box is a hetzner grove, so the commander runs infra's `hetzner.grove.probe grove-3`   # o7
  then the probe reads status.json over its own reach (owed, infra#64) and renders the same line
    backup: ✓ 20m ago · 3 put · 9 skipped
  and a stale or failed status reads the same `✗ STALE` / `✗ FAILED · <cause>` as on ec2
  and if status.json is absent, the probe prints `backup: ✗ NOT ENROLLED`, never a blank row
when [t3] the agent was never installed                                           # o5
  then the verify prints ✗ grove backup · NOT ENROLLED, and the fix is
    rhx grove.provision --what <backup bundle> --mode apply
when [t4] the walk finds no unit in any seat (the service sandboxed away from /home, a path typo)   # b13
  then status.json reads { verdict: failed, cause: "no units found", put: 0, skipped: 0 }
  and the verify prints
    ✗ grove backup · FAILED · no units found under /home/*
       └─ a run of zero units is never a ✓; read the walk: journalctl -u grove-backup -n 50
when [t4.fault] reach is ok and units are found, but one put fails at run time (an s3 5xx, a blip, the temp disk full)   # b20
  then that unit is retried once; if it fails again, it is named and the rest still land
  and status.json reads { verdict: failed, cause: "put failed: <unit>: <error>", put: 11, skipped: 0 }
  and the verify prints
    ✗ grove backup · FAILED · 1 of 12 units did not land
       └─ svc-quotes.feat-x: no space left on /var/tmp; journalctl -u grove-backup -n 50
  and a run with any unit not landed is never a ✓, however many others did
when [t5] `rhx grove.backup.get --from grove-1 --list`, or a restore, with no credential or no bucket name   # l3, l4, r16
  then it lays naught, prints no list, and exits non-zero with the same cause and fix as [t1] / [t2]
    ✋ ConstraintError: cannot reach the backup bucket · no aws credential
       └─ owed by ahbode/infrastructure: the grove's roles-anywhere identity (infra#64, part 3)
  and where the credential answers but s3 refuses the read (R=denied), the cause names the verb
    ✋ ConstraintError: cannot reach the backup bucket · access denied: s3:GetObject
       └─ owed by ahbode/infrastructure: the `grove-s3` grant (infra#63)
```
