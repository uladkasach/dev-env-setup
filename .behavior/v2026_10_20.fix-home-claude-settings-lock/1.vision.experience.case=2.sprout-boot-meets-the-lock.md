# case 2 — a sprout boot meets the lock

the densest walk: it crosses rhachet's init, the tree's arrow, the home file, the lock, and the
session that waits on the init.

the director sprouts a new tree. its boot runs `rhachet init`. the hooks adapter's own write is
shielded by rhachet@1.50.0 and lands in `settings.of.repo.json`, as today. but a second writer in
that boot — the one measured to toggle `statusLine` in home — opens `<tree>/.claude/settings.json`,
an arrow to home. the open fails with `EACCES`. home is byte-equal. the init goes on, and the
director's session boots with the repo's own hooks from `settings.of.repo.json`.

## .the edge, and the fail-safe this tree owns

the edge that could cut: if that writer treats `EACCES` as fatal, the init halts and the sprout
does not boot. a lock that bricks every sprout is worse than the leak it cures.

this tree does not own that writer. it owns whether a lock that bricks sprouts ever ships, so the
apply is not reported done until it proves the opposite on a real boot write:

1. after the lock, run a real sprout boot write in this checkout: `npm run prepare:rhachet`, the
   step a sprout's install runs
2. **completes, home byte-equal** → the lock holds, and the report says so
3. **halts on `EACCES`** → fail safe: keep the strip, restore the write bit, and halt to the
   director with the writer's stack and the exact command — the lock waits for the pair tree
   (`rhachet.beav.fix-enroll-never-writes-home-scope`)

so the director never meets a halted sprout: either the init is proven to survive the lock, or the
lock is lifted before the director's next sprout.

the error's own loudness is the writer's; what teaches the fix is this tree's `plan`, which names
the lock, the hook count, and the one command.

```
given [c2] home settings locked + clean; a tree whose .claude/settings.json is an arrow to home
  when [t0] that tree's boot runs rhx init
    then the boot writer's open of the arrow fails with EACCES
    then ~/.claude/settings.json is byte-equal to the before
    then the init completes, and the session boots with hooks from settings.of.repo.json
  when [t1] rhx grove.provision --what 5.3.brains --mode plan
    then verify ✔ — zero role hooks, no write bit

given [c2.b] the same, but the boot writer treats EACCES as fatal
  when [t0] the apply's post-lock gate runs npm run prepare:rhachet
    then the gate sees the halt
    then the write bit is restored; the strip stays; zero role hooks remain
    then the apply exits ✋ "the lock halts rhachet init; it waits for the pair" with the writer's
      stack and the command, so the director carries it up
```
