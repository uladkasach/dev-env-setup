# 1.vision — the home claude settings hold no role hooks, and only dev-env-setup writes them

## .the defect, measured

`~/.claude/settings.json` holds 22 hooks that rhachet roles authored for a repo. claude reads that
file in every session on this laptop, so the hooks fire in every repo — the commander's sprouts
included.

**the writer is live, and a sprout is one.** measured 2026-10-20 in this very tree:

| fact | evidence |
|---|---|
| this tree's settings name points at home, two hops deep | `.claude` → `.agent/.actors/actor.via.repo=ambient/brain/.claude`; `settings.json` → `settings.of.grove.json` → `/home/vlad/.claude/settings.json` |
| a process of this sprout's boot wrote **home**, four times, through that arrow | four backups `settings.2026-10-20T14-34-{27,27,40,41}Z.<pid>.bak.json` beside the arrow, four distinct pids |
| each write changed home | backups alternate: no `statusLine` → `statusLine` → none → `statusLine`; each backup is the state the NEXT write replaced |
| net home content after boot = pre-boot content | `diff` of home vs the first backup is empty; all 22 role hooks remain |
| the `1 updated` the init printed landed in-tree | `git diff` shows `statusLine` added to `settings.of.repo.json` only |

⇒ every sprout boot opens `~/.claude/settings.json` for write and rewrites it. today the net change
was zero; the hooks already in the file arrived the same way. the write follows the symlink (the
arrow survives each write), so it opens the target in place — which a read-only mode refuses.

**two writers, not one.**

| writer | how it writes | reaches home today? | does `0444` stop it? |
|---|---|---|---|
| `rhachet-brains-anthropic@0.4.3` | `fs.writeFile(<dir>/.claude/settings.json)` — `dist/domain.operations/hooks/config.dao.js:53-58`. opens in place, follows the arrow | ✋ no — `rhachet@1.50.0` wraps it in `withBrainDirSettingsShield`, which swaps the arrow for a real copy, folds the write into `settings.of.repo.json`, and relinks | ✔ yes, where the shield is absent (an older rhachet in some tree) |
| the sprout install step | `git.tree.behavior` runs the repo's `prepare:rhachet` (`rhachet init --hooks`) on the PINNED pre-shield roles, before `rhx upgrade`. that is the adapter above with no shield around it, so it writes `<tree>/.claude/settings.json` through the arrow. wrote the four `settings.<ts>.<pid>.bak.json` files and toggled `statusLine` | ✔ yes — measured, see below | ✔ — the adapter opens in place (`fs.writeFile`), which `0444` refuses |

why the backups prove home was written, not a shield copy: backup #1 is byte-equal to the home file
(224 lines, no `claudeMdExcludes`), while a shield copy holds `settings.of.repo.json` (~530 lines).
so each backup captured the arrow's target — home — and two of them hold a `statusLine` home does
not hold now. a writer added it to home and took it out, twice.

the writer is the sprout install step, named by the director (seed S2). its cure — an install that
never runs a pre-shield init through the arrow — belongs to a separate crew and is out of this
tree's scope. this tree's lock is the guard. the clamp proves `0444` against an `open`-writer; the
boot gate (case 2) proves it against the real one.

**what the strip does NOT break.** an enrolled claude loads its role hooks via
`--settings settings.of.repo.json` (`rhachet@1.50.0` `setBrainDirSettingsLayout.js:17`,
`asBrainCliSpawnArgs.js:11`), which outranks the grove file. so role hooks in home are pure
duplicate for an enrolled session, and pure leak for every other one.

## .the outcome world

**before.** the commander opens claude in a scratch dir. `route.drive` fires, `check-permissions`
blocks `ls`, `memory.guard` calls a `node_modules` that does not exist there, and the stop hook asks
about a radio. none of those roles were enrolled there. he did not choose any of it, and the next
sprout boot quietly rewrites the file again.

**after.** `~/.claude/settings.json` holds the commander's keys and his own hooks, and no
`"author": "repo=…"` hook. its mode is `0444`. a sprout boots; a writer in its init tries to write home
through the arrow and gets `EACCES`, and the home file is unchanged. whether that error reaches the
screen is the writer's choice — a writer that swallows errors fails quietly — so the guarantee this
tree owns is **home unchanged**, and the `verify` is how the commander sees it held. role
hooks live where they belong: in the repo's own settings, which claude merges only in that repo.

when dev-env-setup itself must change the file, `5.3.brains` builds the new content in a locked tmp
beside it and renames that tmp over the file, in one apply. the live file is never writable, not
for an instant. the commander never runs a `chmod`.

**the aha:** the leak has a writer in every tree, so a cleanup alone decays at the next boot. the
lock is what turns a cleanup into a state.

## .the contract, testdriven

one owner, one entrypoint — the extant `5.3.brains` bundle grows the strip and the lock:

```sh
rhx grove.provision --what 5.3.brains --mode plan     # verify runs: names each role hook + the mode
rhx grove.provision --what 5.3.brains --mode apply    # backup → strip + merge into a 0444 tmp → rename → gate
```

plan, on today's file:

```
   ✋ ~/.claude/settings.json holds 22 role-authored hooks, which fire in every repo
      ├─ repo=bhrain/role=driver      5
      ├─ repo=bhrain/role=learner     1
      ├─ repo=ehmpathy/role=mechanic 14
      ├─ repo=bhuild/role=behaver     1
      └─ repo=bhuild/role=dispatcher  1
      fix: rhx grove.provision --what 5.3.brains --mode apply
   ✋ ~/.claude/settings.json is writable (mode <live mode>), so any tree's init can write it
      fix: rhx grove.provision --what 5.3.brains --mode apply
```

apply:

```
   • backup → ~/.claude/settings.2026-10-20T15-02-11Z.<pid>.bak.json
   • role hooks stripped → 22 removed; every unauthored hook kept
   • claude settings merged → ~/.claude/settings.json (0444, swapped in by rename)
   • boot gate: npm run prepare:rhachet completed, home byte-equal → the lock holds
```

a foreign write, after:

```
$ node -e "require('fs').writeFileSync(process.env.HOME+'/.claude/settings.json','{}')"
Error: EACCES: permission denied, open '/home/vlad/.claude/settings.json'
```

the shapes:

- **role hook** = a hook entry whose `author` begins `repo=`. the strip drops those entries, then any
  matcher block left with no hooks, then any event left with no blocks, then `hooks` if empty. an
  entry with no `author` is the commander's — kept
- **every other key** — `env`, `model`, `permissions`, `statusLine`, all of them — untouched by the strip
- **backup** = a byte copy beside the file, before any write, named like the extant `.bak.json` set.
  a failed backup halts the half before any tmp is built
- **skip** = a file that holds the patch, no role hook, and no write bit is never opened: no backup,
  no tmp, `[KEEP]` — the guard the global config half already uses. any one of the three unmet → apply
- **lock** = mode `0444`, set on the tmp BEFORE the rename
- **the owner's write path** (the wish's "unlock") = tmp beside the file → `chmod 0444` → `mv` over.
  a rename needs the DIR writable, never the file, so the live file is never writable. the extant
  upsert already writes by `mktemp` + `mv`; it gains the `chmod` and moves its tmp beside the file
  (the global config half's guard 2). an interrupt before the `mv` leaves the original untouched
- **boot gate** = after the rename, a real sprout boot write (`npm run prepare:rhachet` in this
  checkout, the step a sprout's install runs) must complete
  with home byte-equal. if the init halts on `EACCES`, the apply keeps the strip, restores the write
  bit, and halts to the director — a lock that bricks sprouts never ships ahead of the pair
- **verify** grows two claims: zero role hooks, and no write bit on the file

## .the clamp

`.play/permanent/prove.claude-home-settings-refuses-a-foreign-write.play.sh` — a sandboxed `HOME`
under the repo's fixture dir, never the real one:

1. seed a settings file with role hooks + commander keys; symlink an arrow to it, as a tree does
2. **red arm**: with no lock, a write through the arrow succeeds — calibrates that the probe bites
3. run the upsert against the sandbox
4. **green arm**: the same write through the arrow fails with `EACCES`, file byte-equal
5. role hooks = 0, commander keys equal before, mode `0444`

the red arm is the proof the clamp has teeth: revert the lock, the play goes red.

## .mental model

> "dev-env-setup owns my home claude file. it is read-only; only the 5.3.brains apply opens it.
> role hooks belong to repos, not to my laptop."

analogy: `/etc/hosts` with a managed block — one tool owns it, a hand edit is the exception.

## .evaluation

**pros**
- the strip and the lock ride the bundle that already owns the file — no second writer, no new skill
- the lock catches every writer that opens the target, not only the one we know of
- a foreign write now fails, where today it succeeds silently; loud wherever the writer surfaces its
  errors, as `fs.writeFile` and rhachet's shield both do

**cons**
- `0444` guards against accident, never intent: the same uid can `chmod` it back. every writer we
  know of is an accident, so it suffices
- claude's own writes to the user settings fail while locked (c6)
- a write by atomic rename onto the arrow's path replaces the symlink in the actor dir, not home —
  safe for home, but it severs that tree's arrow (not this tree's defect to fix)

## .open questions & assumptions

- **[answered]** does every role hook carry `author: repo=…`? yes, 22 of 22 in the live file. an
  unauthored hook is kept as the commander's; a role that writes no author would survive (F2)
- **[answered]** is `statusLine` kept? yes — the wish: every key that is not a role hook stays
- **[answered]** do enrolled sessions lose their hooks? no — `--settings settings.of.repo.json`
  (rhachet@1.50.0). bare, unenrolled sessions in a linked repo do; see awkward
- **[answered]** does the lock reach cloud groves? yes, by inference: the bundle runs everywhere, and
  a laptop-only branch is a divergence with no physical reason. surfaced to the wisher in the report,
  as it widens what the wish named
- **[answered, best guess]** `0444` or `chattr +i`? `0444` — no root per apply; F1 at 80%, clean rework
- **[research]** the riskiest: does claude start cleanly with a read-only user settings file? the
  extant brief (`define.claude-code-config`) does not say. measured at execution: lock, then launch a
  fresh `claude`; the 5.3 verification stone holds the result
- **[research]** does claude write the file in normal use (`/model`, "always allow")? measured the
  same way. if yes, those in-app edits fail; read-only is the wish, so accepted, and reported
- **[answered]** who wrote home four times? the sprout install step's pre-shield `rhachet init
  --hooks` (seed S2). it is the adapter, which opens in place, so `0444` refuses it. the boot gate
  still re-proves it on a real init; a changed home there would flip F1 to `chattr +i`
- **[research]** on `EACCES`, does a sprout's init halt or continue (case 2)? for the shielded adapter
  the code answers: the shield rethrows the writer's fault (`withBrainDirSettingsShield.js:65-66`),
  but the adapter never meets the lock, since the shield diverts it. for the unknown writer, the
  same sprout boot measures it. a halt is reported to the director as a pair blocker

## .what is awkward

- read-only fights claude's own "remember this" writes. the commander gives up an in-app edit to gain
  a file no tree can poison
- the fix lives in the GUARD; the writer stays live until the paired rhachet tree ships. until then,
  every sprout boot prints an `EACCES` it did not print before — noise that is, honestly, the alarm
- the strip deletes by an `author` convention the roles own, not this repo
- a bare, unenrolled `claude` in a linked repo reads project settings — which IS home, via the
  arrow — so after the strip, role hooks no longer run there. enrolled sessions are unaffected
  (`--settings settings.of.repo.json`). this is rhachet's chosen layout; the strip only stops home
  from masking it
