# 1. vision — brain-budget-utilization

> a bash alias to see the usage left on any claude code subscription, by auth token, with
> the token sourced from keyrack across all orgs.

---

## the headline (read this first)

two mechanisms can read the numbers; the vision **prefers the direct API**, with the TUI
snapshot as a documented fallback:

- **primary — the direct endpoint.** claude code's `/usage` panel is backed by an undocumented
  HTTP endpoint, `GET https://api.anthropic.com/api/oauth/usage`, that returns the exact numbers
  (5-hour %, 7-day %, opus %, reset times) as structured JSON when called with a subscription
  OAuth token. clean to parse, no TUI. ✓ wisher-preferred.
- **fallback — the TUI snapshot.** `claude /usage` renders an interactive widget, but it *can*
  be driven in a subshell and snapshotted (e.g. via a duct) if the endpoint ever fails or
  changes. usable, but a screen-scrape — kept as a backstop, not the default.
  ⚠️ **NOT BUILT — deferred, and it needs the wisher's answer.** see the 2026-09-02 amendment
  below. the shipped feature has exactly one leg.

the token in both cases is a **subscription OAuth token** (`CLAUDE_CODE_OAUTH_TOKEN`, from
`claude setup-token`), tied to a Pro/Max/Team plan — an `ANTHROPIC_API_KEY` (pay-per-use) has
**no "subscription usage left."** these tokens live in the **global keyrack**, one key per
subscription, so the check works from any repo (brain auth from anywhere). **two aliases**
deliver this: one to **store** a token, one to **view** usage.

---

## ✓ amendment (2026-09-02): the TUI fallback is **STRUCK** — the read has one leg, by ruling

the headline above promises a two-legged read: the direct endpoint, with a TUI snapshot as the
backstop. **only the first leg was built**, and as of 2026-09-02 only the first leg is
required — the wisher was asked directly and answered *"no tui fallback"*.

so this section reads in two parts, and the order matters. the first part is the case that was
put to the wisher. the second is their ruling on it. the case did not close the requirement;
the ruling did.

**why it was not built.** the case below is about the fallback's own merit, and it is worth a
read before anyone builds it:

- **a screen-scrape fails in the worst direction.** the endpoint fails loudly with an http code
  that the error table already names. a scrape fails when the widget's layout shifts and it
  parses the new shape into *confident wrong numbers*. for a tool whose whole job is to warn
  about a budget, a wrong number is worse than a refusal — it is the failure the shape-check
  (`unexpected_shape`) exists to prevent on the primary leg, re-introduced on the backstop.
- **it fights the one-holder invariant.** `claude /usage` reports on whoever is *signed in*, so
  a fallback sweep over N accounts would have to swap the live login N times — N credential
  mutations, each with the blast radius `brains.auth.use` spends five guards on, to serve a
  read. the primary leg needs no swap at all.
- **it is a second reverse-engineered dependency**, not a hedge against the first. both legs
  break on the same event (anthropic changes how usage is exposed); the scrape simply breaks
  later and more quietly.

**the case above was never a waiver, and it was not treated as one.** the reviewer's correction
was accepted in full: *why a fallback is undesirable to build* is a different claim from *the
wisher struck the requirement*, and until the wisher was asked, only the first had been made.
so the requirement was held **open** across every review round rather than argued shut, and the
two closes were named rather than assumed.

### ✓ the ruling — 2026-09-02

asked directly, the wisher answered **"no tui fallback"**. the requirement is **closed by
removal**. the case above is what they ruled on, so it stands as the accepted rationale for a
single-leg read — not a rationalization written after the fact.

what the strike does NOT do:

- **it does not retire the risk.** the endpoint is still undocumented and still
  reverse-engineered. that stays recorded as `hazard.claude-usage-endpoint-is-undocumented.md`,
  with the failure signature and the one cause to rule out first (a stale pinned UA 429s and
  *looks like* a retirement).
- **it does not close the door.** `_brains_auth_usage_reply` is a pure leaf, so if the endpoint
  ever dies, a second source is an addition beside it rather than surgery through it. the seam
  outlives the requirement.

**every line in this vision that promises a TUI-snapshot backstop is superseded by this
ruling.** as with the `--sub`→`--reach` amendment below, the original text is left in place
rather than rewritten, so the shift reads as a decision rather than disappears as an edit.

**what was built instead**, so the single leg is legible when it breaks:

- `hazard.claude-usage-endpoint-is-undocumented.md` records the failure signature, the one
  cause to rule out first (a stale pinned UA 429s and *looks like* a retirement), and the moves
  open if the endpoint dies.
- the 429 hint now names the stale-UA cause and its override, so the one failure a retry can
  never clear stops to report itself as "retry shortly".
- the endpoint call is a pure leaf (`_brains_auth_usage_reply`), so a second source is an
  addition beside it rather than surgery through it.

## ⚠️ amendment (2026-08-31): an account is named by its **reach**, not by a slug

this vision was first written against a `--sub <slug>` scheme: the human invents a handle
(`ehmpathy`, `ahbode`), and the key is filed under
`BRAINS_AUTH__OF__CLAUDE_CODE_OAUTH_TOKEN__FOR__<slug>`.

**that scheme is retired.** an account is now named by its **reach** — the email address the
oauth token itself reports:

```
brains.auth.usage  [--reach <email>|@all] [--json] [--help]
brains.auth.set    [--reach <email>]
brains.auth.use    [--reach <email>]
```

**why it changed.** a slug is a handle the human invents, so it is a second name for what
already has one — and a second name can disagree with the first. it also had to be typed
correctly at store time, and a typo would silently file a subscription under a name no later
read would look for.

the reach removes the invention entirely. `/api/oauth/profile` answers "who does this token
belong to?" with an email, so the token states its own name, and that name is derived fresh on
every call rather than recorded. `brains.auth.set` therefore takes **no argument in the common
case** — it signs you in, asks the token who it is, and files it under the answer. `--reach`
survives only to confirm an expected account.

**the consequences worth a note:**

- a reach is an email address, so it is **validated as one**. `@all` is the only non-email
  value any of the three commands accepts.
- the rendered rows are keyed by email, so a `--json` consumer reads
  `.["kai@ehmpathy.com"].five_hour.utilization`, not `.ehmpathy…`.
- `--sub` still parses as an alias of `--reach`, so an older invocation does not error — but
  it is **not** the term, and a bare slug (`--sub ehmpathy`) is now a keyrack miss, because no
  key is filed under a bare slug any more.

**every line below that says `--sub <slug>` is superseded by `--reach <email>`.** the original
text is left in place rather than rewritten, so the shift reads as a decision rather than
disappears as an edit.

## the outcome world

### day-in-the-life

vlad runs several claude code subscriptions — one per slug (ehmpathy, ahbode, ahction…). each
has its own 5-hour and weekly budget. today, the only way to know "how much have i burned on
the ehmpathy sub this week?" is to open a claude code session on that login and eyeball the
`/usage` TUI — one session per subscription, no way to compare, no programmatic path.

after this wish: one command in any terminal.

```
$ brains.auth.usage
🐢 claude budget — across all subscriptions

  ehmpathy   ██████░░░░  58% session   ·  ███░░░░░░░  31% week   ·  opus  12%
             └─ session resets in 2h14m  ·  week resets fri 09:00

  ahbode     █████████░  91% session   ·  ██████░░░░  64% week   ·  opus  40%
             └─ session resets in 0h48m  ·  week resets sat 14:00  ⚠️ session nearly spent

  ahction     ░░░░░░░░░░   3% session   ·  █░░░░░░░░░   9% week   ·  opus   0%
             └─ session resets in 4h51m  ·  week resets sun 20:00
```

#### ⚠️ amendment (2026-08-31): what shipped, and the two places it departs from this mock

```
🧠 claude budget
   ├─ casey@ahction.com: ✋ refresh token dead (run: brains.auth.set)
   ├─ vlad@ahbode.com  ← signed in
   │  ├─ session  ██░░░░░░░░  24% used  ·  resets at mon 13:20, in 2h41m
   │  └─ week     ████░░░░░░  48% used  ·  resets at tue 12:00, in 25h21m
   └─
```

the accounts are named by reach, and the two windows sit on their own lines with both an
absolute reset time and a countdown — all per the wisher's direct instruction. two smaller
departures were judged rather than instructed, so they are recorded here:

- **the header is `🧠 claude budget`, with the `— across all subscriptions` suffix dropped.**
  🧠 was a wisher instruction. the suffix went because the render is no longer always "all" —
  `--reach kai@x.com` renders one account under the same header, and a header that claims
  every subscription while it shows one is a small lie told on every narrowed read.

- **there is no `⚠️ nearly spent` badge.** the bar already carries that signal: a nearly-full
  bar is legible at a glance, which is the whole reason the number is rendered as *used*. a
  badge that fires on most reads of a heavily-used account trains the eye to skip badges, and
  the one that then matters is skipped with the rest. the row still earns attention by its
  fill, so no signal is lost.

both are pinned in the snapshot suite (`render.opus-row`, `render.healthy`), so neither can
drift silently, and both are clean reworks if the wisher prefers the mock.

| | before | after |
|---|--------|-------|
| check one sub | open a claude session on that login, read `/usage` TUI | `brains.auth.usage --sub ehmpathy` |
| compare all subs | impossible | `brains.auth.usage` (one screen) |

the value clicks the first time a session hits a limit mid-flow. instead of "which sub do i
switch to?" being a blind guess, one command shows every sub's remaining headroom side by
side — so you switch to the one with budget, before you burn the one without.

## user experience

### usecases / goals

- **triage before a big run** — check budget along two axes: *this week* ("do i have enough
  weekly budget on ehmpathy to drive this release, or should i run it on ahction?"), or *for a
  peer on that org* ("does the token a teammate shares on ehmpathy still have headroom, or have
  they burned this week's cap?").
- **pick the freshest sub** — mid-session limit hit → see which subscription has headroom.
- **monitor a shared/bot sub** — is the seaturtle[bot] subscription near its weekly cap?
- **automation** — feed `--json` into a statusline, a cron alert, or a dashboard.

### the contract (inputs & outputs)

primary surface — a shell function backed by a dotted-namespace alias (the extant convention in
`src/bash_aliases.sh`: `machine.usage.*`, `report.usage.ram.*`, `use.*`). this feature opens a
new `brains.auth.*` namespace that echoes the `BRAINS_AUTH__` key prefix:

```
brains.auth.usage [--sub <slug>|@all] [--json] [--help]
```

| input | sense | default |
|-------|-------|---------|
| `--sub <slug>` | one subscription, by its key slug | `@all` (every stored subscription) |
| `--sub @all` | every `BRAINS_AUTH__OF__CLAUDE_CODE_OAUTH_TOKEN__FOR__*` key | (the default) |
| `--json` | raw endpoint JSON per subscription, for automation | off (renders the tree) |
| `--help` | usage + example | — |

a **subscription** is identified by the slug of its keyrack key —
`BRAINS_AUTH__OF__CLAUDE_CODE_OAUTH_TOKEN__FOR__<slug>`, stored in the **global keyrack**
(`--org @all` = the key is accessible from any repo, regardless of cwd — so the check works
even outside a specific repo, i.e. brain auth from anywhere). each slug names one distinct
subscription, decoupled from keyrack org/env. `--sub @all` sweeps every such key.

output (default): a turtle-headed tree, one block per subscription, with session %, week %,
opus %, and reset times, and a `⚠️` when a window is nearly spent.

output (`--json`): the raw `/api/oauth/usage` body per subscription, keyed by slug.

#### the companion alias — add a token

a second alias adds a subscription's OAuth token into the global keyrack under the
`BRAINS_AUTH__OF__CLAUDE_CODE_OAUTH_TOKEN__FOR__<slug>` pattern, so it is reachable from any
repo:

```
brains.auth.set --sub <slug>
```

| input | sense |
|-------|-------|
| `--sub <slug>` | names the subscription; becomes the key slug |

it runs `claude setup-token` (browser flow), captures the emitted token, and writes it via
`keyrack set --org @all --key BRAINS_AUTH__OF__CLAUDE_CODE_OAUTH_TOKEN__FOR__<slug>`. this is
the one-time setup that `brains.auth.usage` then reads.

#### the third alias — swap the live login (amended 2026-08-31, wisher-confirmed)

```
brains.auth.use [--reach <email>]
```

| input | sense |
|-------|-------|
| `--reach <email>` | the stored account to sign the global claude cli in as |
| (no args) | report which account is signed in right now |

**why it was added.** the read-only pair above answers "which account has budget left?" — and
then leaves the human to act on the answer by hand, through claude's own `/login` browser
flow, once per switch. that is the move the whole feature exists to inform, so the vision's
own day-in-the-life ("mid-session limit hit → switch to the one with headroom") was only half
deliverable without it. `use` closes that loop.

**why it is in scope.** the wish's frame is a *fleet* of subscriptions: `--org @all`, one key
per account, "any given claude code subscription". a fleet you can measure but not steer is
half a tool. `set` (enroll) and `usage` (measure) without `use` (select) leaves the fleet
read-only.

**what it costs — the risk this amendment owes.** `use` is the only command here that mutates
a credential, and it is the highest-blast-radius code in the feature:

| risk | how it is held |
|------|----------------|
| overwrites `~/.claude/.credentials.json`, the file that backs live sessions | a `.bak` restore point is written before the replace, and the failure messages promise it only when the file is actually there |
| the prior account's ONLY live token sits in that file | it is read out (`park_read`) BEFORE the overwrite and filed to the keyrack AFTER — install-then-park, so one token never has two holders |
| the mint rotates the target's stored token server-side | the install-failure path files the rotated value back, so a failed swap cannot strand the target |
| a swap done behind our back (a manual `/login`) | identity is DERIVED from the live token on every run, never remembered; a swap refuses unless that identity is api-VERIFIED |
| claude's own profile view left behind by the swap | `sync_profile` rewrites `~/.claude.json` after the install |

**what it does not do.** no `--json` contract, unlike its two siblings — deliberately. `use` is
an interactive, one-at-a-time act a human performs and reads; a machine-readable contract for a
credential swap invites an unattended caller to drive it, which is a footgun the fleet does not
need. that asymmetry is a choice, recorded here so it is not read as an oversight.

#### ⚠️ amendment (2026-09-01): the skill proxy is NOT part of that asymmetry — it was a gap

this paragraph originally withheld **two** items from `use` under one justification: the
`--json` contract *and* a skill proxy. that bundle was wrong, and it made the riskiest command
in the feature the least safe to invoke.

the two are not the same kind of item:

- **`--json`** is an output contract. it is what invites an unattended caller. the argument
  holds, and `use` still has none.
- **a skill proxy** is reachability. `rhx brains.auth.use` adds no affordance a human who types
  `brains.auth.use` in their shell does not already have — it is the same interactive command.

and the argument for the proxy is *strongest* for `use`, which is what makes its absence an
inversion rather than a gap. the proxies exist because **a human's shell may hold an older copy
of the alias**. for `usage`, a stale copy renders stale numbers. for `use`, a stale copy mutates
credentials with whatever logic it was loaded with — a shell that predates the compare-and-swap
guard will install over an account that arrived mid-flight and destroy its only live token. so
the one command where "do I have the current code?" genuinely matters was the one command with
no way to answer yes.

`brains.auth.use.sh` now exists, clamped alongside its siblings against the `--skill` hang.
`--json` remains withheld, on the original argument.

**the fulcrum, flagged not decided.** an alternative was to split `use` into its own wish and
ship the read-only pair alone. that stays a clean rework — `use` is additive and touches
neither `set` nor `usage` — so it can be lifted out later without a teardown.

### what it looks like to leverage them

```
# one-time — add a subscription's token to the global keyrack
$ brains.auth.set --sub ahbode

# the common case — all subs at a glance
$ brains.auth.usage

# just one sub
$ brains.auth.usage --sub ahbode

# in automation — feed a statusline or alert
$ brains.auth.usage --json | jq '.ahbode.five_hour.utilization'
```

### the timeline a user goes through

1. (one-time, per subscription) `brains.auth.set --sub <slug>` — runs `claude setup-token`
   and stores the token in the **global keyrack** under
   `BRAINS_AUTH__OF__CLAUDE_CODE_OAUTH_TOKEN__FOR__<slug>`.
2. `brains.auth.usage` — enumerates the stored subscription keys, reads each token from the
   global keyrack (`keyrack get --org @all … --value`), hits the usage endpoint once per token,
   and renders the tree.
3. read the budget; act (switch sub, throttle, or proceed).

## the mechanism (test-driven)

one leaf call per token:

```sh
curl -s https://api.anthropic.com/api/oauth/usage \
  -H "Authorization: Bearer $TOKEN" \
  -H "anthropic-beta: oauth-2025-04-20" \
  -H "User-Agent: claude-code/$CLAUDE_VERSION" \
  -H "Content-Type: application/json"
```

- the `User-Agent: claude-code/<version>` header is **load-bearing** — without it the request
  lands in an aggressively rate-limited bucket and returns persistent `429`s (community
  finding). the function must send a real claude-code UA string.
- response is JSON with five-hour and seven-day windows (+ opus), utilization and reset times.
  the tree is a `jq` render of that body.

to read the tokens from the global keyrack (conforms to `howto.source-aws-creds` in ghlitch —
keyrack unlock runs in a subprocess, so we `get --value` the secret, we don't rely on env
propagation): enumerate the subscription keys, then read each one.

```sh
rhx keyrack list --json                                              # find *__FOR__* subscription keys
rhx keyrack get --org @all \
  --key BRAINS_AUTH__OF__CLAUDE_CODE_OAUTH_TOKEN__FOR__<slug> --value
```

### the fallback mechanism (only if the endpoint fails)

if the undocumented endpoint ever changes or 4xxs, the same numbers can be read by a subshell
snapshot of the `/usage` TUI — driven headless and captured via a duct (`src/ductwork.sh`), then
parsed from the rendered widget. slower and brittle (a screen-scrape), so it stays a documented
backstop, never the default.

## mental model

### how a user describes it to a friend

> "it's like `df -h` for my claude subscriptions — one command shows how much budget's left
> on each, so i know which one to run my next job on."

### analogies that fit

- **fuel gauges on a fleet** — several tanks (subscriptions), one dashboard.
- **`df -h` for AI budget** — capacity remaining, per mount (per sub).
- same shape as the extant `report.usage.ram.*` — "gauge a resource," applied to claude budget
  instead of RAM.

### their terms vs our terms

| user says | we say |
|-----------|--------|
| "usage left" / "budget left" | `utilization` — the share **spent**, labelled `% used` (see below) |
| "the 5-hour limit" | `five_hour` window / session window |
| "the weekly cap" | `seven_day` window |
| "which sub" | which account, named by its reach (an email) |
| "auth token" | `CLAUDE_CODE_OAUTH_TOKEN` (subscription OAuth token) |

#### ⚠️ amendment (2026-08-31): the number rendered is **used**, not **left**

this vision first said "we render left = 100% − used, so the user still reads 'left'." the
implementation renders **used**, and this table now says so.

**why.** the two framings need opposite bars, and an unlabelled bar is read by its fill:

- render **left**, and a nearly-spent account draws an almost-empty bar
- render **used**, and a nearly-spent account draws an almost-full bar

a full bar reads as "at the limit" to nearly everyone, and that is the reading that matches the
danger. under the *left* framing the same account looks nearly empty, and a human who reads the
bar before the label throttles when they had room — or, worse, proceeds when they did not. so
the number is `used`, the word `used` sits beside every bar, and a full bar means a spent
window.

**this is a flagged fulcrum, not a settled term.** the wisher never confirmed either framing; it
was best-guessed. to flip it is a **clean rework** — one label and one subtraction, no caller
depends on the direction (`--json` passes the endpoint's own `utilization` through untouched
either way). raised here for the end-of-road council rather than decided in silence.

## evaluation

### how well it solves the goal

- **strong** on the core intent: see budget-left per subscription, by token, read from the
  global keyrack — all delivered in one command, from any repo.
- **it inverts the wish's stated frame** ("usage left") into what the endpoint returns
  ("utilization used"); we render **used**, with the word `used` beside every bar, so a full
  bar means a spent window (amended 2026-08-31 — see the terms table above for why, and for
  the clean rework that would flip it).

### pros

- one command, all subs, comparable side by side — impossible before.
- automatable (`--json`) — unlocks statuslines, alerts, dashboards.
- reuses the machine's keyrack + the extant `.usage.` naming — low surprise.
- no dependency on a claude session being open.

### cons

- **the endpoint is undocumented and reverse-engineered.** anthropic can change or remove it
  with no notice. mitigated by the `/usage` TUI-snapshot fallback, but that path is brittle too.
  this is the biggest risk.
- **per-sub token setup is still a step** — but now a one-liner via `brains.auth.set` (in scope),
  not a manual chore.
- OAuth-token lifecycle: the setup-token is long-lived, but the usage endpoint may want a
  fresh *access* token (refresh flow) — needs validation (open question).

### edge cases & pit-of-success

| edge case | how the contract keeps the user safe |
|-----------|--------------------------------------|
| a stored token is an API key, not an OAuth token | detect the `sk-ant-api…` prefix, render `— not a subscription token` for that slug, don't 401 silently (failfast, not failhide) |
| no claude OAuth tokens in keyrack | print the setup path (`brains.auth.set --sub <slug>`), not an empty tree — errors name the fix |
| endpoint returns 429 | surface "rate-limited — retry shortly"; confirm the UA header is being sent |
| endpoint returns 401 / expired token | say "token expired — re-run `brains.auth.set --sub <slug>`", name the slug |
| token expired mid-`@all` sweep | render the other subscriptions; mark the failed one, don't abort the whole sweep |
| `--json` consumer | emit valid JSON even on partial failure (per-slug error objects) |

## open questions & assumptions

each question is triaged as `[wisher]` (only the wisher knows), `[research]` (settle at
blueprint via a live call), or `[answered]` (settled now by logic/docs/tooling).

### `[wisher]` — requires wisher input

1. ✓ **CONFIRMED (2026-07-28) — mechanism.** prefer the direct `GET /api/oauth/usage` endpoint;
   the `/usage` TUI subshell-snapshot (via a duct) is kept as a documented fallback only.
2. ✓ **CONFIRMED (2026-07-28) — token type.** store subscription OAuth tokens
   (`CLAUDE_CODE_OAUTH_TOKEN`), not the pay-per-use `ANTHROPIC_API_KEY`.
3. ✓ **CONFIRMED (2026-07-28) — key scheme.** keys are
   `BRAINS_AUTH__OF__CLAUDE_CODE_OAUTH_TOKEN__FOR__<slug>` in the **global keyrack**
   (`--org @all` = repo-independent, reachable from any cwd). each slug = one subscription.
   this dissolves the earlier `--org` overload: subscription identity is the key **slug**,
   not the keyrack org.
4. ✓ **CONFIRMED (2026-07-28) — alias names.** `brains.auth.set --sub <slug>` (store) and
   `brains.auth.usage --sub <slug>|@all` (view). a new `brains.auth.*` namespace that echoes the
   `BRAINS_AUTH__` key prefix.
5. ✓ **CONFIRMED (2026-07-28) — setup.** the wisher will run setup; the `brains.auth.set` alias
   is now **in scope** (was previously deferred) to make adding a token a one-liner.

### `[research]` — settle at blueprint via a live call

- **exact response shape** of `/api/oauth/usage` — field names for utilization, window
  bounds, reset timestamps, opus. groundwork confirmed the endpoint + windows exist; the
  precise keys need a live call with a real token (which we don't have yet).
- **setup-token vs access-token** — does the endpoint accept the long-lived setup-token as
  Bearer directly, or must we refresh to a short-lived access token first? community monitors
  read `~/.claude/.credentials.json`; keyrack storage of the setup-token may need a refresh step.
- **`anthropic-beta` header currency** — confirm `oauth-2025-04-20` is still the value the
  endpoint expects (single-source today).
- **key discovery** — confirm `keyrack list --json` surfaces the global-keyrack
  `*__FOR__*` subscription keys, so the sweep can enumerate them and `get` each by full key
  name (one `get` per subscription, no bulk `--value` dump — sidesteps the earlier
  multi-value-shape and secret-exposure concern).
- **rate-limit on an `@all` sweep** — N stored tokens means N sequential calls to the same
  endpoint. even with the correct `User-Agent`, a burst may trip a shared limit. the blueprint
  must check whether a small delay or a sequential (not parallel) sweep is needed.
- **token storage mechanism / TTL** — keyrack stores the API keys as `PERMANENT_VIA_REPLICA`.
  will a `CLAUDE_CODE_OAUTH_TOKEN` store the same way, and does that interact with the
  setup-token→access-token refresh question above? verify the stored form at blueprint.

### `[answered]` — settled now

- **is `--org @all` a real keyrack flag?** yes — `keyrack get --help` shows `--org <@this|@all>`

## groundwork

sanity-checked against reality; not exhaustive.

### external research

the wish references `claude /usage` and the anthropic backend — both verified:

- **`claude /usage` has no structured stdout.** `/usage` is an interactive TUI widget with no
  CLI / JSON / stdout contract — confirmed by three open feature requests that request exactly
  this: [anthropics/claude-code#40395](https://github.com/anthropics/claude-code/issues/40395),
  [#24459](https://github.com/anthropics/claude-code/issues/24459),
  [#32796](https://github.com/anthropics/claude-code/issues/32796). it *can* still be
  subshell-snapshotted (a screen-scrape of the rendered widget, e.g. via a duct) — the wisher
  confirmed this — so it survives as the fallback, but the structured endpoint is preferred.
- **the real endpoint exists.** `GET https://api.anthropic.com/api/oauth/usage`, headers
  `Authorization: Bearer <oauth_token>`, `anthropic-beta: oauth-2025-04-20`,
  `User-Agent: claude-code/<version>` (UA is required or you get rate-limited to `429`).
  returns five-hour + seven-day (+opus) usage windows as JSON. sources:
  [SessionWatcher usage guide](https://sessionwatcher.com/guides/how-to-check-claude-code-usage),
  [Claude-Code-Usage-Monitor#202](https://github.com/Maciek-roboblog/Claude-Code-Usage-Monitor/issues/202),
  [Anthropic authentication docs](https://code.claude.com/docs/en/authentication).
- **token type.** `CLAUDE_CODE_OAUTH_TOKEN` from `claude setup-token` is the subscription
  OAuth token (Pro/Max/Team/Enterprise); an `ANTHROPIC_API_KEY` is pay-per-use with no
  subscription-usage concept. source: Anthropic authentication docs (above).

### internal research

- **keyrack contract** — verified live. `rhx keyrack get` takes `--key`, `--env`,
  `--org <@this|@all>`, `--value`/`--output`. the wish's "keyrack --org @all" = `keyrack get
  --org @all`. `rhx keyrack list --owner ehmpath --json` shows **no** `CLAUDE_CODE_OAUTH_TOKEN`
  entries today — only `ehmpathy.test.ANTHROPIC_API_KEY` and non-claude keys.
- **keyrack sourcing pattern** — `howto.source-aws-creds.[lesson].md` (ghlitch): unlock runs
  in a subprocess so env vars don't propagate back; use `keyrack get --value` to capture the
  secret in the calling shell. this feature follows the same pattern.
- **alias conventions** — `src/bash_aliases.sh`: dotted namespace aliases backed by
  `_underscore_functions` (e.g. `machine.usage.diagnose` → `_machine_usage_diagnose()` at
  `:119,132`; `report.usage.ram.swap` → `_report_usage_ram_swap()` at `:145,190`). the new
  `brains.auth.*` names follow this same dotted convention. secrets are pulled with `jq`
  (older aliases use `op get item`; we use `rhx keyrack get`).
- **repo-as-source-of-truth** — `rule.require.repo-as-source-of-truth`: the alias lives in
  `src/bash_aliases.sh`, synced via `sync.devenv.bashaliases` — never hand-edited on the host.

## what is awkward?

- **an undocumented endpoint as a dependency.** the whole feature rests on a reverse-engineered
  endpoint anthropic never promised. it fights the "solve-at-cause / use the intended API"
  instinct — there simply is no intended API yet. mitigated by the `/usage` TUI-snapshot
  fallback and by isolation of the endpoint call, so a future official API is a one-line swap.
- **~~`--org` overload~~ — RESOLVED.** an earlier draft feared keyrack's `--org` (which org's
  copy) would collide with the user's "which subscription" model. the wisher's key scheme
  removes the collision: `--org @all` just means *global keyrack* (repo-independent), and the
  **subscription is the key slug**, a separate namespace. so the two never overload.
- **~~setup prerequisite~~ — RESOLVED.** an earlier draft flagged that the viewer is inert until
  a token is stored. the `brains.auth.set` alias (now in scope) folds that setup into a
  one-liner, so the feature is self-contained.
