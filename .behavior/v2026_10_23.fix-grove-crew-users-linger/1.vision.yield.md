# 1.vision — one tmux crash never takes every crew on a grove

## .the outcome world

### before

- every crew on a grove talks to ONE tmux server: `/tmp/tmux-1002/default`
- that server is the jammy package, `tmux 3.2a-4ubuntu0.2`, and it segfaults at one offset
  (~110 times in ~3h on grove-ahbode-v20260901)
- one segfault ends every mechanic, foreman, and reflector on the box at once
- no core lands: `systemd-coredump` is absent, so each crash is a kernel log line and naught else
- linger is granted by `1.6.4.keyrackd`, a bundle about a different subject, and only on its
  happy path (see groundwork). it held on this box by luck, not by declaration

### after

- `rhx grove.provision --mode apply` on a fresh grove puts down:
  - tmux **3.5a**, built from a sha256-pinned release tarball into `/usr/local/bin`
    — the same version `git.grove.keepalive --mode tmux` hand-placed on the live box
  - `systemd-coredump`, so the next crash leaves a core `coredumpctl` can open
  - linger for **every** login seat, read per seat before set, in a bundle that owns it
- the `2.8.tmux` verify asserts the tmux on PATH **is the pinned build**, never "a tmux"
- the crew verbs (nheuron) start one tmux server per crew via the extant
  `DUCTWORK_TMUX_SOCKET` seam, so a crash costs one crew and the rest work on

### the aha

> today's verify printed `tmux present (3.2a) ✔` on the box that crashed 110 times.
> after: it prints `✋ tmux 3.2a is not the pinned 3.5a`, and an apply converges it.
> and if 3.5a ever crashes too, one crew drops, a core lands, and the human reads the stack.

## .mental model

- to a friend: *"one tmux held every crew, like one power strip under every desk. we swapped
  in a strip that does not short, put a breaker on each desk, and a fault recorder on the wall."*
- the human says "tmux crashed"; we say "the tmux server segfaulted". a crew owner says
  "my crew died"; the cause is a shared server, not their crew.

## .evaluation

| goal (wish outcome) | met by | gap |
|---|---|---|
| 1. find + cure the crash | pinned 3.5a build; coredump to catch the next one; per-crew servers dispatched | the trigger is a hypothesis until reproduced on 3.2a (see open questions) |
| 2. linger guaranteed | a linger bundle that reads every seat | — |
| 3. clamps red→green | `prove.*.play.sh` per fix | the crash clamp needs a 3.2a binary to run against |
| 4. infra dispatch | read: userdata installs neither tmux nor linger | no same-source fix owed there (F4) |
| 5. pr + watch | — | — |

pros: provision now reproduces what keepalive did by hand; a crash is diagnosable; the verify
no longer passes a crash-prone build.
cons: a source build means a compiler toolchain + `libevent-dev`, `libncurses-dev`, `bison`
on every grove, and a build on first apply.

edgecases:
- a camper apply cannot install to `/usr/local/bin` → decline via `bundle.root.owns`, fix-text
  `sudo -v && …` / run as ground (`gotcha.rhx-runs-a-skill-with-no-tty`)
- apt later reinstalls tmux 3.2a into `/usr/bin` → the verify reads `command -v tmux`, so a PATH
  that resolves to `/usr/bin/tmux` is caught ✋
- a 3.2a server still alive after the swap → a 3.5a client may meet a protocol mismatch.
  configure verify already walks every live socket; it gains a per-server version read
- a tampered or re-tagged tarball, or a failed build → ✋, prior tmux untouched (cases 7, 8)
- 🛑 a per-crew server started from INSIDE another crew's pane sits in that crew's cgroup, its
  spawner (a short client) dead, not the cgroup's oldest — so after 24h `1.6.6.abandoned`
  (`machine_resource_procs_reap_abandoned`: ours · spawner dead · not its cgroup's oldest ·
  older than 24h) reaps it. the nheuron dispatch must start each crew's server in a scope of its
  own (its own ssh session, or `systemd-run --user --scope`), and this repo's clamp proves the
  reaper spares a server so started
- `1.6.6.abandoned`'s header names `1.6.4.keyrackd` as the seat of linger; the new linger
  bundle dispatches before both, and both headers point at it

## .open questions & assumptions

1. **[research] the trigger.** tmux's own CHANGES for 3.3a lists *"Do not crash when run-shell produces
   output from a config file"*; our `tmux.conf` ends with `run '~/.tmux/plugins/tpm/tpm'`, and the
   crash bursts read as "a fresh server dies at once". that fits, at ~60% confidence. execution
   reproduces it against the apt 3.2a binary on a probe socket before any claim lands in a brief.
   ⇒ if the reproduction confirms it, the conf's `run` line is also made silent (its output
   sent nowhere), so any box still on an older tmux stops on that path too. the build stays
   either way: it is the dictated cure, and 3.2a→3.5a carries other crash fixes.
2. **[research] does 3.5a crash on the same path?** the reproduction from (1) runs against the
   3.5a build too; the long tail is answered by coredump on the live box.
3. **[answered] does a 3.5a client reach a still-live 3.2a server?** yes on protocol: both
   define `PROTOCOL_VERSION 8` (`tmux.h:69` @ 3.2a, `tmux-protocol.h:23` @ 3.5a, read via
   `gh api`). commands whose features 3.2a lacks may still refuse; such a server is retired at
   its crew's next revive.
4. **[answered] do crews reach this repo's `duct.*`?** no. nheuron `crewwork.sh:188` sources its
   own `work/ductwork.sh`, whose `DUCTWORK_TMUX_SOCKET` is empty by default (a test seam), so
   crews share the default server today. F3 holds.
5. **[wisher] where does the per-crew server live?** best guess: nheuron, as a dispatch from
   this route (F3, 70%). if "the provision fix should carry one server per crew" meant code in
   this repo, say so — the rework is clean.
6. **[wisher] pin 3.5a or the latest 3.8?** best guess 3.5a, for parity with the live box (F1).
7. **[wisher] build on the laptop too?** best guess yes, one rule for every box (F2, 60%).

## .groundwork

### external research

- tmux 3.5a release: `gh api --method GET repos/tmux/tmux/releases/tags/3.5a` →
  `tmux-3.5a.tar.gz`, published 2024-10-05. the sha256 is measured at execution and pinned
- latest is 3.8 (2026-09-09); see F1
- tmux `CHANGES` @ 3.5a: crash fixes between 3.2a and 3.5a include line 216 (3.3a, run-shell
  output from a config file) and line 79 (3.5, focus on a pane that exits)

### internal research

- `src/grove.provision/2.shell/2.8.tmux/provision.upsert.sh` step 1: `pkg_install tmux` — the
  jammy 3.2a path
- `.../2.8.tmux/provision.verify.sh`: `tmux present ($(tmux -V…)) ✔` — any version passes
- `.../2.8.tmux/tmux.conf:304`: `run '~/.tmux/plugins/tpm/tpm'`
- `.../2.8.tmux/_.sh`: `grove_provision_2_8_tmux_live_sockets` already enumerates every server
- `.../1.6.4.keyrackd/provision.upsert.sh:47` — returns before linger when the prune skill is
  absent; `:119` — returns ✔ when `$USER` lingers, never reads other seats; `:145` — a failed
  grant is 🌙
- `src/grove.web.sh` — `web_fetch` + `web_verify_sha256` are the wire boundary for the tarball
  (`rule.require.verify-binary-downloads`)
- nheuron `define.work-primitive-hierarchy.md:172` and `skills/work/ductwork.sh:74` —
  `DUCTWORK_TMUX_SOCKET` is the seam for one server per crew; ductwork threads it through every
  tmux call
- ahbode/infrastructure `genGroveHibernatorUserData.ts` — creates ground and camper, installs
  `unzip curl` + awscli; no tmux, no linger
- clamps in this repo are `.play/permanent/prove.*.play.sh`
- this box today: `rhx grove.provision --what 2.8.tmux --mode plan` → `tmux present (3.5a) ✔`

### relayed, not measured here

📌 unverified in this route — each is owed a read at execution before code leans on it:
- the crash counts, offsets, and `3.2a-4ubuntu0.2` version — from the wish's on-box read
- `/usr/local/bin` as the build's path, and `systemd-coredump` present — from the wisher's
  message; the plan above measured only the version
- keepalive's build recipe (configure flags, deps) — its source is on no nheuron ref this
  route can read (`rhx git.repo.get lines --in uladkasach/nheuron --words keepalive` → one
  unrelated hit on origin/main); the provision recipe is derived independently
- PATH order under a non-interactive ssh command (`/usr/local/bin` before `/usr/bin`) —
  assumed from ubuntu's `/etc/environment`; `gotcha.a-tool-found-by-path-answers-only-a-human`
  says a transport's PATH is exactly where this breaks
- "the live server keeps its old inode" (case 3) — true only if the install writes a new file
  and renames it over the old; a write in place over a live executable fails `ETXTBSY`. the
  upsert must install to a temp path and `mv`, and the clamp must hold a live server across an apply
- the build's duration — unmeasured; measured at execution
- "a crash leaves a core" — a package present is not a core stored. `core_pattern` must pipe to
  systemd-coredump, and an ssh-started server carries its session's core limit. the verify and
  its clamp crash a probe server (`SIGSEGV`, own socket) and assert `coredumpctl` lists the pid

## .what is awkward

- a C build on every grove is heavy for one binary; it is the honest cost of a pinned version
  apt does not ship for jammy
- the per-crew split — the half that actually bounds the blast radius — lives in another repo,
  so this route ships the substrate and a dispatch, not the split itself
- linger moves out of `1.6.4.keyrackd`; that bundle then reads a fact another bundle owns
