## 1. `1.6.4.keyrackd` — it DID dispatch to cloud, and would not have worked

no `GROVE_ENV_SERVER` gate existed, so the bundle was already reached on every box
class. three defects made that hollow.

### a) LINGER — the cause, and why it went unnoticed

> a `systemctl --user` manager starts at a seat's first login and STOPS at its last
> logout.

every prior user timer in this repo (`1.6.2.monitor`, `4.3.4.snapshot`,
`6.5.onepassword`) was born on a laptop, whose graphical session never logs out and
so holds the manager up for free. **`1.6.4.keyrackd` is the first user timer that
applies to a grove**, whose only login is the duct.

⚠️ and `is-enabled` / `is-active` CANNOT see it. both answer from inside a live user
manager, so on a grove they read ✔ right up to the moment the pane closes and the
manager dies with them. neither can observe its own mortality.

⇒ linger is a THIRD claim, and the only one that outlives the session that asks it.
granted per `5.8.docker`'s precedent — only a sudo seat may set it, so ground sets it
for every human seat, camper included.

⚠️ it is a 🌙 on `local@*` and a ✋ on cloud — the exact INVERSE of `1.6.2.monitor`'s
gate (that leaf needs a desktop bus; this one needs a session that persists, which a
desktop already supplies). a ✋ on the laptop would go red where the timer plainly
runs, and a check seen to cry wolf gets silenced along with the grove's real one.

### b) the 🌙's reason was stale

it claimed the skill is absent because `--from src` leaves `.agent/` behind.
`git.grove.provision.boot.sh:312` pushes `--from .` **precisely so a grove can reach
its skills**. the guard is still right; the reason was not. corrected.

### c) the ExecStart binds a CHECKOUT

measured: the installed unit names `~/git/more/dev-env-setup` while this run is a
worktree. a `--from tree` apply would repoint a PERMANENT timer at a dir
`git worktree remove` can delete. the drift ✋ the plan prints is the mechanism at
work, not a false alarm. noted at the reader: apply this bundle `--from main`.

## 2. the npm→pnpm override — my first verdict was WRONG

i reported "for a human only". measured on `grove-ahbode-v20260901`:

```
duct pane (interactive zsh)      → npm is a shell function        ✔
bash -c descended from that pane → npm is a function {…}          ✔   ← the robot path
fresh interactive bash           → npm is a function {…}          ✔
ssh host '<cmd>' (fresh session) → /home/camper/…/fnm/…/bin/npm   ✋
```

`.zshrc:210` **exports** `BASH_ENV=~/.bash_aliases`, so every `bash -c` a robot
spawns under the duct inherits it and sources the file.

⇒ the discriminator was never human-vs-robot. it is **whether the caller inherits
`BASH_ENV`**. i measured the bare-ssh path alone and generalized from it —
`gotcha.a-check-that-cries-wolf-gets-silenced`, q4: a sign-off broader than its rows.

the only miss is a FRESH ssh session, which is `--bare`, whose two triggers are both
bootstrap-time.

## 3. the finding neither question asked for — a STALE DUCT

ground's pane answered `-bash: type: npm: not found` and `BASH_ENV=` empty. both
records are correct:

```
ground:x:1001:…:/usr/bin/zsh          ← 2.5.zsh converged it
camper:x:1002:…:/usr/bin/zsh
.bashrc:104  . ~/.bash_aliases        ← 2.7.aliases converged it
```

and `bash -ic 'type npm'` on that same seat returns the function. so the files are
right and the pane is wrong. one cause:

> **the duct outlives the provision.** a tmux server caches `default-shell` at server
> start; a pane sources its rc once at pane start. a box provisioned AFTER its duct
> opened has a correct `$HOME` and a stale shell.

confirmed: `tmux show-options -g default-shell` → `/bin/bash`, while the passwd record
says zsh.

⚠️ **no verify can see this.** every verify reads the FILES, and the files are right.
`2.5.zsh` goes green while every pane on that box runs the wrong shell — the inverse
of `rule.require.judge-declared-state-not-live-state`: declared state correct, live
state stale.

⚠️ and `term=duct.refresh`'s repair ladder has no row for it. `refresh` repaints,
`reboot` kills the pane's program, `stop` kills the session. a stale shell needs
`reboot`, and no line says so.

### the two ways to close it

| option | cost |
|---|---|
| a verify claim in `2.5.zsh` — compare tmux's `default-shell` to the passwd record, fix-text names `duct.reboot` | ~15 lines; must stay silent where no tmux runs, or it cries wolf on the laptop |
| `git.grove.provision boot` reboots the duct as its last step, before the gate | closes it by construction, no new check to keep honest |

the second makes the stale pane impossible rather than merely reported, but it touches
the boot sequencer — flagged, not decided.

## the tooling friction met on the way

- `git --no-pager diff -- <path>` is not on the allowlist; `git diff <paths>` is
- `--what 'a || b'` is refused by `git.grove.send` — one step per send, by design
- the cross-repo hook reads a REMOTE absolute path as a local cross-tree access, so a
  `git.grove.send --what 'bash ~/git/more/dev-env-setup/…'` is blocked from here
