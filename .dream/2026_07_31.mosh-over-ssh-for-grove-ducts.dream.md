dream = mosh, as an option for humans

## .what

make it **possible** for a human to reach a grove over **mosh** (mobile shell), so their
interactive duct survives a jittery link, a roaming ip, and a closed laptop.

additive only. ssh stays exactly as it is — every skill (`git.grove.push`, `send`, `pull`,
`wake`) keeps its ssh transport untouched. this dream adds a door; it removes none.

mosh authenticates *via* ssh — extant keys and `~/.ssh/config` just work — then hands the
session off to its own udp channel. so it rides the alias `git grove wake` already writes.

## .the name

**mosh = MObile SHell.** "mobile" in the roaming sense, not the phone sense: the shell
follows you as your network moves under you. it is a deliberate echo of `ssh` — one
syllable, four letters, drop-in — so `mosh host` reads as the sibling of `ssh host`.

## .why

the pain is typing latency, and it is a **human** pain. a 475ms spike stalls every
keystroke, because ssh will not paint a character until the server echoes it back. an
automated command does not care; a person typing does.

three things mosh does differently:

| what | how it helps a human at a duct |
|---|---|
| **local echo with prediction** | mosh guesses what a keystroke does and paints it at once (briefly underlined), reconciling when the server confirms. typing stops being hostage to the round trip |
| **udp + state sync, not a byte stream** | ssh is an ordered tcp stream, so one dropped packet head-of-line-blocks everything behind it. mosh syncs *screen state*: on loss it skips to the current frame instead of replaying. output during a dropout resyncs rather than queueing then dumping |
| **roaming** | the session survives an ip change — wifi → cellular, laptop closed and reopened hours later. ssh drops on all of those |

## .why it fits THIS repo

**a duct is tmux** (`term=duct._.choice._.md`), and mosh keeps no scrollback of its own —
it only tracks the current screen. alone that is a dealbreaker; here it is irrelevant,
because tmux already owns the scrollback. `mosh + tmux` is the canonical pairing, and the
duct is already the tmux half of it.

so a human just reaches the same duct through a different door:

```sh
mosh <grove> -- tmux attach -t <duct>     # the human's door
ssh  <grove> -t tmux attach -t <duct>     # unchanged; what every skill keeps using
```

## .the shape

mosh is a **bundle**, not a one-off (`rule.require.install-via-procedures`):

- a new bundle under `src/grove.provision/2.shell/` — `provision.upsert` installs mosh
  (`apt install mosh` / `brew install mosh`), `provision.verify` proves the binary is there
- it must land on **both ends**: the grove needs `mosh-server`, the desktop needs the client
- the bundle is the whole of it. no skill changes, no transport decision, no call-site edits —
  because the ssh path is not touched

## .the prerequisite — a udp path must exist

mosh needs udp 60000–61000 reachable on the grove. today `git.grove.wake` findserts an
**ssm port-forward** and writes an ssh alias pointed at `127.0.0.1:<port>` — a *tcp*
tunnel, which mosh's datagrams cannot ride.

so the human door only opens where a direct udp path exists. that is a security-group +
reachability ask for whoever provisions groves — worth confirming **before** installing
anything, since the bundle is cheap and the network posture is not.

this is a prerequisite for the mosh door, not a question about the ssh one. if the answer is
"no udp", not one thing regresses — the ssh path was never in play.

## .open questions
