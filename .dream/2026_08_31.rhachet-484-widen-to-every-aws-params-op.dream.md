## .why that scope is too narrow

`set` is the op the defect was FOUND on, never the op it is about. the cause sits at the
identity layer — `asKeyrackAwsParamIdentity` accepts IMDS, and an SSO profile is not IMDS — and
every `aws.params` op reaches that same layer. so `get`, `list`, and `fill` are all subject to it
on the same box; `set` is merely the one that got typed first.

⚠️ **a bug titled for the op it was found on invites a fix scoped to that op**, and a fix scoped
to `set` would leave three callers broken with the issue closed. the title is the spec a fixer
reads.

## .the shape of the widening

- retitle from `cannot write an @all slug` to one that names the LAYER, e.g.
  *"aws.params rejects an SSO profile at the identity layer, so no op works from a laptop"*
- name the four ops in the body, so the fix has a checklist rather than one example
- keep the original `set` reproduction — it is the measurement, and it stays

## .the asymmetry worth a line in the body

a cloud grove is exclusively ec2, so IMDS is always there and the slug works. a laptop has no
IMDS, and that absence costs it no capability today **only because a local box authes itself by
hand and never reads the slug**. so the defect stays invisible until a human tries to place or
read a credential from their own machine — which is exactly what `set` was doing.
