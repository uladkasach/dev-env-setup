## .why deferred, not dropped

the human, 2026-07-28: *"for now, we just dont want the git diff"*.

the branch already carries a large rename (`sync.<old>.*` → `grove.provision.*`, ~40 files) plus
a driver rework. to add a 9-file move on top would bury the reviewable change under a wall of
renames — and a reviewer who cannot see the change cannot catch a defect in it. so the file
rename waits for its own commit, where the diff is *only* renames and reads in one pass.

this is a clean rework: a move plus a reference update, no teardown, no behavior change.

## .why it is worth a look at all

`rule.require.grove-provision-as-the-only-verb` binds the CONTRACT layer, and the human
deliberately bounded it there: *"keep the files called install_env._.sh; but the command should
be called grove.provision"*. so the current split is **sanctioned, not a violation** — this dream
proposes to reach past what the rule requires, and that is why it is a dream rather than a task.

the case for the reach:

- a traveler who greps `grove.provision` finds the command and not the code that implements it
- the entrypoint's own filename is the first thing a new reader sees, and it says the retired
  word
- `grove.bootstrap.sh` already speaks the new vocabulary at the same layer, so the suite is
  the odd one out

the case against, recorded honestly:

- the FUNCTION names (`install_zsh`, `install_rust`) should NOT follow. at step level `install`
  is often literally true — `install_zsh` runs `apt install zsh` on a package that was genuinely
  absent. it is the TREE as a whole, which always already exists, that is upgraded
- so the dream renames FILES only, which leaves a file named `grove.provision.pt2.shell.sh` full
  of `install_*` functions. that is defensible (the file is the upgrade's part 2; the functions
  install packages) but it is not obviously tidier than today
- git history follows a rename, but `git log --follow` is per-file and blame gets a hop

## .the open question to settle first

does `grove.provision.pt2.shell.sh` read better than `install_env.pt2.shell.sh`?

the `pt<N>` sequence exists to order how the files load, and it reads as a chapter list of an
INSTALL. under the new name it reads as chapters of an UPGRADE, which is truer to what the
driver does — but the parts themselves are still mostly installs. worth one honest look before
the move, rather than a mechanical find-and-replace.
