## .why `unix.duct` / `unix.term` and NOT `sshbash`

three separate reasons, and each one alone is sufficient.

### 1. `sshbash` names two mechanisms; neither is the environment

`ssh` is a transport. `bash` is a shell. the *environment* is a terminal surface a human or robot
drives. so the name is wrong on both halves:

- a **local** duct uses no ssh at all
- a duct on this repo's machines holds **zsh**, not bash

so `sshbash` would be a false name in the common case, and a name that is false is worse than a
name that is vague — it teaches the reader a wrong model.

### 2. it cannot express the LOCAL case, and that case is the whole point

`dev-env-setup` already settled this, and paid for it. its `duct.uri` uses an **empty authority**
for a local duct, on the `file:///` precedent:

```
duct://grove-1/main/mechanic     # a duct on a remote grove
duct:///main/mechanic            # a duct on THIS machine
```

one grammar, both cases, and a caller that does not care which. `sshbash` has no way to say
"this machine" — its own name asserts a remote hop. an environment named after its transport can
never cover the transport-free case, and a second environment for local would be two lists of the
same knowledge.

### 3. it repeats a mistake this repo has already made once

`install_env` → `grove.provision` was a rename for exactly this reason: the old word named the
**mechanism** (a one-time install) where the act was a **convergence** (drive the machine to the
declaration). `sshbash` → `unix.duct` is the same correction, one layer up.

> name the surface, never the wire that reaches it.

## .the two environments, and where the line falls

they are two layers, not two names for one layer. `dev-env-setup` has independently grown both,
which is the evidence that the split is real and not invented for this dispatch:

| environment | the surface | what it drives | this repo's extant skills |
|---|---|---|---|
| **`unix.term`** | the terminal *emulator* — windows, tabs, splits, focus, font, what a human's eye is pointed at | the frame | the `termwork` briefs; kitty window/tab management |
| **`unix.duct`** | the durable *session inside* the frame — a named tmux session that outlives every client | the program held | `duct.open`, `duct.send`, `duct.read`, `duct.reboot`, `duct.refresh`, `duct.stop`, `duct.list` |

the line: **`term` owns what a human LOOKS at; `duct` owns what the machine RUNS.** a duct
survives when every term that showed it is gone — that is what makes it durable, and it is why the
two cannot be one environment.

### the duct verb set is settled, and worth lifting whole

it is not a bare send/read pair. it is a **repair ladder**, ordered by cost, and the ordering is
the knowledge:

```
duct.refresh   free       repaint the client; kills not one program
duct.reboot    cheap      kill the HELD program; the session and its cwd survive
duct.stop      expensive  kill the session itself
```

a driver that only has `stop` will reach for `stop`, and lose the session for a repaint. the ladder
exists because that happened. lift the ladder, not just the verbs.

## .why the PLAYWRIGHT is the right owner

the human: *"thats who should know how to use them"*. the argument, spelled out:

### a play is already the unit, in both repos, invented independently

`dev-env-setup` grew `.agent/playbooks/*.play.sh` plus a `--play` transport on `git.grove.send`,
for a reason it wrote down: a chained one-liner sent to a machine **cannot be reviewed, repeated,
or diffed**, and the repo's own pretooluse hooks read only the OUTER command — so every step
hidden inside a `--what` string reaches a machine unexamined. its `git.grove.send` now *refuses* a
chained `--what` and names the play as the fix.

that is the same conclusion a browser playwright reached about driving a browser. **two
implementations of "a play" would drift**, which is the defect this repo has retired twice
(`install_env.grove.sh`, the rsync/tar layout). so centralize the `.play.sh` convention in
bhrowser, under the playwright, and let `dev-env-setup` consume it.

### the playwright already holds the hard-won part

authorship of a play for an interactive surface is a genuine craft: idempotence, a wait that is
not a `sleep`, output read without a race, a failure that names its fix. the playwright has that
craft for browsers. a terminal is a *simpler* surface than a browser, not a different kind of one.

## ⚠️ .why it must be a human-authorized escalation

this is the part that must not be softened. a browser play is bounded by a browser. a
`unix.duct` play is **arbitrary code execution on a machine** — every guarantee the harness has
rests on the outer command string, and a play is by design a payload the outer string does not
show.

so the capability cannot be ambient. it is granted.

### reuse the extant `*.uses` meter — do NOT invent a mechanism

both orgs already have this exact shape, twice over, with three-level precedence:

| meter | grants |
|---|---|
| `git.commit.uses` | how many commits a mechanic may make, and whether it may push |
| `radio.uses` | whether a dispatcher may broadcast at all — global / org / local |

so: **`unix.uses`**, with the same precedence (`global blocked` overrides org, org overrides
local, unset = blocked). the whole design is proven, the vocabulary is familiar, and a third
authorization mechanism would be a third list.

```sh
rhx unix.uses get                          # what am i allowed to drive?
rhx unix.uses allow --org ehmpathy         # a human grants it
rhx unix.uses block --global               # a human revokes everything, everywhere
```

### the safe default is `blocked`, and the ladder should be per-verb

not every duct verb carries the same blast radius, so a single on/off wastes the distinction:

| verb | radius | sensible default |
|---|---|---|
| `duct.list`, `duct.read` | READ-ONLY — observe only | allowed |
| `duct.refresh` | repaints a client; kills not one program | allowed |
| `duct.send` | **arbitrary execution** | granted |
| `duct.reboot`, `duct.stop` | kills a program / a session | granted |

read is free, write is granted. that is the same line `git.commit.uses` draws between `stage` and
`push`.

### the counter-evidence that proves granted-not-ambient

on 2026-07-29, in a session where `rule.require.reach-a-grove-through-its-duct` was booted into
context **and had been read aloud**, a robot ran raw `ssh grove-1` roughly **ten times in one
hour**. the human had to ask: *"why do you need direct ssh grove-1 ever?"*

the rule was read, believed, agreed with, and lost to convenience — because the raw capability was
*present*. `rule.prefer.prevent-over-correct` is the lesson: a constraint holds for every driver
every time; a rule relies on the driver to remember it while in a hurry.

> so the escalation is not paperwork. it is the mechanism by which the rule becomes true.

## .what the dispatch should deliver

1. **two environments** — `unix.term` and `unix.duct`, with the layer line stated: term = what a
   human looks at, duct = what the machine runs
2. **the skill sets**, lifted whole from `dev-env-setup`:
   - `unix.duct.{list,read,open,send,reboot,refresh,stop}` — with the repair ladder's ORDER
     documented, since the ordering is the knowledge
   - `unix.term.*` — window/tab/split/focus, per the `termwork` briefs
3. **the duct.uri grammar** — `duct://<host>/<tree>/<role>` and `duct:///<tree>/<role>`, with the
   empty-authority-means-local convention and the `file:///` precedent that justifies it
4. **`unix.uses`** — the escalation meter, modeled on `radio.uses`, per-verb, default blocked,
   reads free
5. **the `.play.sh` convention, centralized** — one definition of a play, one authorship guide,
   consumed by both repos. include the argument for why a chained `--what` is refused
6. **the playwright's authorship guide for a terminal surface** — the craft notes that differ from
   a browser: no DOM to await, so a wait is a prompt-match or an output-match, never a `sleep`; a
   read races the write; a duct is durable so a play must be idempotent against a session that
   already exists
