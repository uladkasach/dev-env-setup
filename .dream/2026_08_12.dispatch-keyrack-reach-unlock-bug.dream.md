## task — `@all` + `--reach` is write-only: unlock never matches the address

**title:** `keyrack: machine-wide @all keys cut for a --reach can never be unlocked`

**severity:** blocker-class for any `--org @all` + `--reach` credential — the pair the reach
feature most obviously invites, since a machine-wide account credential is exactly what a reach
(an email) names.

---

### .what

a key cut at a reach under `--org @all` can be **set**, **got**, and **deleted**, but never
**unlocked**. because unlock is the gate that populates the daemon, the credential is effectively
write-only: every later read reports `locked`, forever.

### .the isolation (what works vs what does not)

verified live against `rhachet@1.46.0`, one probe key, four commands:

| command | `--reach` | result |
|---------|-----------|--------|
| `keyrack set` | ✅ works | files `@all.prep.KEY@casey@ahction.com`, with `slug` + `reach.exid` stored as separate fields — exactly the documented model |
| `keyrack del` | ✅ works | removes by address |
| `keyrack get` | ✅ works | finds the host, correctly reports `status: locked 🔒` |
| `keyrack unlock` | ❌ **fails** | `blocked: key not found in manifest: KEY` |

so the defect is **isolated to `unlock`** — but since `get` can only ever answer `locked` until
`unlock` populates the daemon, the whole read path is dead.

> ⚠️ note for anyone who reproduces this: `keyrack get --reach --unlock` ALSO fails, because
> `--unlock` delegates into the same broken path. test **bare** `get --reach` to see that `get`
> itself is healthy. this distinction is easy to miss and led us to misdiagnose it once.

### .black-box repro

```sh
# 1. cut a key at a reach, machine-wide
echo "PROBE-VALUE" | rhx keyrack set --owner $OWNER --org @all --env prep \
  --key BRAINS_AUTH__PROBE --reach casey@ahction.com \
  --vault os.secure --mech PERMANENT_VIA_REPLICA
# => ✅ @all.prep.BRAINS_AUTH__PROBE@casey@ahction.com

# 2. confirm the manifest holds it, with slug + reach as separate fields
rhx keyrack list --owner $OWNER --json | jq '.[] | select(.reach)'
# => { "slug": "@all.prep.BRAINS_AUTH__PROBE", "reach": { "exid": "casey@ahction.com" }, ... }

# 3. unlock it — FAILS
rhx keyrack unlock --owner $OWNER --env prep \
  --key BRAINS_AUTH__PROBE --reach casey@ahction.com
# => ✋ blocked: key not found in manifest: BRAINS_AUTH__PROBE
#    why: ... (nor as a machine-wide @all.prep.BRAINS_AUTH__PROBE)
```

step 3 fails even though step 2 proves the record exists.

### .root cause

`src/domain.operations/keyrack/getAllMachineWideSlugsForEnv.ts:31-40`

```ts
const prefix = `@all.${input.env}.`;
const machineWideSlugs = Object.keys(input.hostManifest.hosts).filter(
  (slug) => slug.startsWith(prefix),
);

if (input.keyAsk)
  return machineWideSlugs.filter(
    (slug) => slug === `@all.${input.env}.${input.keyAsk}`,   // ⛔ here
  );
```

`hostManifest.hosts` is keyed by **address**. for a key cut at a reach the address is
`@all.prep.KEY@casey@ahction.com`, but the filter tests **exact equality** against the
**reachless** slug `@all.prep.KEY`. it can never match. the function also accepts no `reach`
parameter at all — the machine-wide `@all` expansion is reach-blind by construction.

the local variable is even named `slug` while it holds an address, which is likely how the case
was missed: the reach feature made map keys addresses, and this pre-reach call site kept treating
them as slugs.

**sole caller:** `session/unlockKeyrackKeys.ts` (lines 146 and 182) — which is why only `unlock`
is affected.

### .why the fix belongs here (and what shape it takes)

the caller's own loop already does the right thing — it takes each **reachless slug** and
re-applies the reach itself:

```ts
for (const slug of slugsForEnv) {
  const hostFound = getOneKeyrackHostForSlugAtReach({
    hosts: hostManifest.hosts,
    slug,
    reach: input.reach,       // ← reach applied HERE, per slug
  });
```

so `getAllMachineWideSlugsForEnv` should keep its **slug** return contract, and needs no `reach`
param at all. it simply must derive those slugs correctly: read the `slug` **field** each entry
records, rather than the map key.

that also honors the domain rule in `term=address._.choice._.md` — *"a reach exid may legally
hold `@`, so a split back is not well-defined"*. the fix never parses an address; it reads the
field the manifest already stores.

### .the verified patch (reference implementation)

```ts
// ⚠️ the map KEYS are ADDRESSES — `slug@reach` for a key cut at a reach — so read the `slug`
//    FIELD each entry records rather than the key itself. an address must NEVER be split back
//    on `@` (a reach exid may legally hold one, and an email is the intended form), and an
//    exact-equality test against a reachless slug can never match an address that carries a
//    reach. dedupe: N reaches of one slug are N addresses but ONE slug, and the caller
//    re-applies the reach per slug via getOneKeyrackHostForSlugAtReach.
const prefix = `@all.${input.env}.`;
const machineWideSlugs = [
  ...new Set(
    Object.entries(input.hostManifest.hosts).map(
      ([address, host]) => host?.slug ?? address,
    ),
  ),
].filter((slug) => slug.startsWith(prefix));
```

the rest of the function is unchanged. properties:

- **additive** — a reachless entry has `slug === address`, so its behavior is bit-identical
- **dedupes** — N reaches of one slug collapse to one slug, which is what the caller wants
- **no `@` parse** — honors the address rule
- **falls back to the key** (`?? address`) if an entry predates the `slug` field

### .proof (all four run live, `rhachet@1.46.0` + this patch)

| # | check | before | after |
|---|-------|--------|-------|
| 1 | `unlock --reach` on a cut key | ✋ `key not found in manifest` | 🔓 unlocked, echoes `reach: casey@ahction.com` |
| 2 | `get --reach --value` round-trip | (unreachable — locked) | returns the stored value |
| 3 | reachless `unlock` (regression) | 🔓 works | 🔓 works — unchanged |
| 4 | `unlock --reach` at a reach the key was NOT cut for | ✋ blocked | ✋ **still** blocked, with the correct "a reach is never derived" message |

check 4 is the one that matters most: the fix must NOT make a reach-unlock fall back to the
reachless credential — that would hand back a live credential for the wrong account. it does not;
the `getOneKeyrackHostForSlugAtReach` guard still fires exactly as designed.

### .suggested regression test

`getAllMachineWideSlugsForEnv.test.ts` — a host manifest whose entry is keyed by an ADDRESS:

```ts
hosts: {
  '@all.prep.MY_KEY@casey@ahction.com': {
    slug: '@all.prep.MY_KEY',
    reach: { exid: 'casey@ahction.com' },
    // ...
  },
}
```

then assert `getAllMachineWideSlugsForEnv({ env: 'prep', keyAsk: 'MY_KEY', hostManifest })`
yields `['@all.prep.MY_KEY']`. this goes **red** on the current code (yields `[]`) and green on
the patch — the extant 6 tests all use reachless fixtures, which is the coverage gap.

a journey-level test earns its keep too: `set --org @all --reach` → `unlock --reach` →
`get --reach` round-trips a value. the unit test alone would not have caught that this renders a
whole credential class write-only.

### .related

same **shape** as the `@all` read-path defect previously filed (rhachet#440): a machine-wide
`@all` credential that can be written but not read. that one was an absent `org=@all` fallback in
the unlock host-config lookup; this one is an address-vs-slug mismatch in the machine-wide
expansion. both land on `unlockKeyrackKeys`, and both make `@all` write-only — it may be worth a
look at whether the `@all` path wants a shared, reach-aware slug-expansion helper so the next
feature does not have to remember it a third time.

## .local state — retired (kept for the lesson)

while the upstream fix was in flight, the patch was hand-applied to **two** `node_modules`
copies. both are now dead weight: `rhachet@1.47.3` carries the fix, so the correct move is an
upgrade, never a re-patch.

| where | reached by |
|-------|-----------|
| this worktree's `node_modules/rhachet/` | `npx rhx` |
| the global pnpm install | `rhx` |

**the lesson worth keep:** the first pass patched only the worktree copy, and the feature still
broke — because `brains.auth.*` (in `src/bash_aliases.sh`) calls the bare `rhx` from a human's
shell, not `npx rhx` from this worktree.

> when you patch a dependency, first ask which entrypoint the CALLER resolves. the path a tool
> reads is a property of the TOOL, not of your cwd.

a `node_modules` patch is also ephemeral by construction — a `pnpm install` wipes the worktree
copy, a global upgrade wipes the global one. one was lost exactly that way (1.44.4 → 1.44.5).
that ephemerality is why the upstream change was always the real deliverable.

**if `keyrack unlock --reach` ever reports `key not found in manifest` again:** check the
installed version first. below 1.47.3 → upgrade. at or above → it is a new defect, not this one.
