# 🌙 dream: one rack entry carries its own coordinates TWICE, so no consumer can address it

- kind   = fix
- owner  = a human — a `set` has no entry-only mode, so the repair touches a stored value
- caught = 2026-09-29

## .the cue that fired

a rack read, taken to settle the BEAVER vault question, printed 38 entries. one of them is not a
slug any consumer composes:

```
├─ ahbode.prep.ahbode.prep.EHMPATHY_SEATURTLE_GITHUB_TOKEN
│  ├─ env: prep
│  ├─ org: ahbode
│  ├─ mech: PERMANENT_VIA_REPLICA
│  └─ vault: os.secure
```

its two peers three rows up show the shape every other entry holds:

```
├─ ahbode.prep.EHMPATH_BEAVER_GITHUB_TOKEN
├─ ahbode.prep.FIREWORKS_API_KEY
```

⇒ the KEY field of that entry is literally `ahbode.prep.EHMPATHY_SEATURTLE_GITHUB_TOKEN`, so the
rack's own `$org.$env.$key` render repeats the prefix. `env` and `org` are correct; the key carries
a copy of them.

## .the gap, precisely

a slug is an ADDRESS (`term=slug`), and an address is composed by the CONSUMER:

```sh
rhx keyrack get --owner ehmpath --key EHMPATHY_SEATURTLE_GITHUB_TOKEN --org ahbode --env prep
#                                     └─ what every consumer passes
```

no consumer passes `--key ahbode.prep.EHMPATHY_SEATURTLE_GITHUB_TOKEN`, because the `--org` and
`--env` flags already carry those two segments. so:

| the entry | reachable by |
|---|---|
| the 37 well-formed ones | the coordinates their consumers already pass |
| 🔴 this one | a `--key` string no consumer in this repo composes |

⇒ **it is an ORPHAN** — stored, listed, and addressable by nobody
(`term=orphan._.choice._.md`). whatever it holds is unreadable through the rack by any caller
written to the normal contract.

⚠️ **and it reads as healthy.** `keyrack list` prints it beside 37 correct rows with a full mech
and vault; no status field says ORPHAN, and no consumer errors — a consumer that asks for the
well-formed slug gets `absent 🫧`, which names the wrong cause entirely.

## .why it is not done in this round

**it fails SAFE, on the one axis that matters.** the repair is to place the value at the correct
slug and drop the doubled one, and `keyrack set` has no entry-only mode — it acquires a secret and
writes it (`rule.require.github-token-at-all-camp`, its 🛑 block). so:

- a `set` at the correct slug needs the token's VALUE, and the value sits behind the doubled entry
  a consumer cannot address
- the seaturtle token is MINTED at github, so no box holds a source to forward from
- ⇒ a paste is structurally required, exactly as the BEAVER rows are
  (`2026_09_28.beaver-app-blob-has-no-rack-readable-source`)

🟡 and it is **not** on any provision path. no bundle and no gate reads
`EHMPATHY_SEATURTLE_GITHUB_TOKEN` at `ahbode.prep` — that key is the mechanic's commit identity,
and `rule.require.github-token-at-all-camp` states outright that a box reads `@all.camp.GITHUB_TOKEN`
rather than the seaturtle key. so the orphan blocks no grove today.

⇒ which is precisely why it earns a dream rather than a halt: it is a latent defect whose cost
lands on whoever next reaches for that slug and reads `absent 🫧`.

## .the shape of the fix

1. **confirm the repeat is in the KEY, not the render.** read one well-formed entry and this one
   side by side; if `env` and `org` are right and only the composed line repeats, the key field
   holds the copy

   ```sh
   rhx keyrack list --owner ehmpath
   ```

2. **place the value at the correct slug**, on the laptop, with a fresh paste:

   ```sh
   rhx keyrack set --owner ehmpath --key EHMPATHY_SEATURTLE_GITHUB_TOKEN \
     --org ahbode --env prep --mech PERMANENT_VIA_REPLICA
   ```

   🛑 HERE, never on a grove — a `set` prompts, and a tty on the provision path is a blocker
   (`rule.forbid.tty-as-a-proxy-for-a-human`)

3. **drop the doubled entry.** whether `keyrack` offers a `del` for a host entry is unread; if it
   does not, that absence is the reseed half of this dream

4. re-prove: `rhx keyrack list --owner ehmpath` shows 37 well-formed rows and no doubled one

## 🟡 .the reseed half — a rack that ACCEPTS a composed key is the upstream defect

the entry exists because some caller passed a composed slug into `--key`, and the rack stored it
without complaint. that is a pit-of-failure: the flag's contract is one SEGMENT, and a segment with
a `.` in it is never valid.

⇒ so the durable fix is upstream, in `ehmpathy/rhachet`: **`--key` refuses a value that carries a
`.`**, and names the fix (*"pass the key alone; `--org` and `--env` carry the rest"*). one guard
retires this defect class for every rack that will ever exist.

⚠️ it is worth a dispatch rather than a patch here: this repo consumes keyrack and declares none of
it, so a local workaround would be a second reader over another package's contract.

## .what this dream does NOT claim

it does not claim the entry is dead weight. it may hold a live, valid token — the claim is narrower:
**whatever it holds is unreachable through the contract every consumer uses**, so it is
indistinguishable from absent to every caller and distinguishable from absent to a `list`.
