## .the subject

`.agent/repo=.this/role=any/briefs/shell/rule.require.wrap-cli-in-skills.md` — read it as the seed, not
as the deliverable.

its current claim: *any external CLI you need must be wrapped in an `rhx` skill; never run it raw
at the prompt.* enforcement: **blocker**.

## .why lift it at all — it is org-wide, filed as repo-local

the rule lives under `repo=.this/`, which says "a fact of this repo". it is not. every claim it
makes is about **any** repo that reaches **any** external tool:

- reviewable — a named surface a human can allowlist
- repeatable — the next traveler runs a name, not a remembered flag incantation
- fails loud with the fix — a wrapped failure prints the unlock command, not an sdk stack trace
- hides no account confusion — a wrapped read reports the ACTIVE identity before any result

none of that is dev-env-specific. it was authored here because this is where `aws` first bit, and
it has stayed here because nobody moved it. that is the definition of a lesson that has not been
externalized far enough.

## .the six crystallization candidates

the learner's job is to split these out where they generalize, rather than leave them buried in
one rule's prose. each is stated with the dated evidence that earned it.

### 1. the scope is wider than "external CLI"

the `.what` says *external CLI*. this repo has since wrapped three other kinds of invocation
under the same rule, so the stated scope is already smaller than the practiced one:

| what got wrapped | the skill | why the rule reached it |
|------------------|-----------|--------------------------|
| an external CLI | `aws.whoami`, `aws.ec2.get` | the original case |
| a remote reach | the whole `duct.*` + `git.grove.*` family | `reach-a-grove-through-its-duct` |
| a **local play** | `git.grove.push.verify` → `verify.grove.push.layout.play.sh` | `bash <play>` is unallowlisted, unnamed, unrunnable |
| a multi-flag incantation | `git.repo.test`, `git.release` | the flags were the knowledge |

the fourth row is the sharpest, because the wrapped subject is **this repo's own executable** — no
external tool at all. the honest generalization is not *external CLI* but:

> **any invocation whose knowledge lives in the invocation.** if the flags, the paths, the order,
> or the reachability are what you would have to remember, that memory belongs in a named skill.

### 2. "a check nobody can invoke by name is a check nobody runs"

this one deserves its own brief. it is the reason `git.grove.push.verify` exists, and it
generalizes far past CLIs — to tests, to lint gates, to diagnostics.

the dated evidence, from this repo, 2026-07-29:

> a layout check was written as `verify.grove.push.layout.play.sh`. it was correct, complete, and
> **unrunnable** — `bash <play>` is not on the allowlist, so it could not be invoked, so it never
> ran, so the defect it existed to catch (a `src/src/` shadow copy) survived **three** credited
> fixes. the check's absence was invisible because the check *existed*.

the invariant: **an unnameable guard is a guard that has already failed.** a file that asserts a
truth nobody can invoke is worse than no file, because its presence reads as coverage.

this is a **nature** invariant in the sibling dream's taxonomy — not a preference about tooling; it
follows from what "a check" is for.

### 3. the outer-string mechanic — wrapping *unblocks*, it does not merely tidy

the rule buries this in a paragraph, and it is the single most load-bear, least obvious fact in
the file:

> the permission hook evaluates only the **outer** command string, so `rhx <skill>` passes while
> the nested `aws ...` inside stays invisible to it.

so wrapping is not hygiene you do after the work — it is **how the work becomes possible**. a
robot that has not internalized this reads the rule as a style note, defers it, and then fights
the allowlist for an hour. (this session: exactly that, repeatedly.)

generalize it as its own lesson, because it holds for any harness with a command allowlist:

> **the allowlist reads the outer call. so a skill is the unit of trust.** to wrap is to move a
> command from "argued about each time" to "decided once".

### 4. the specialization pattern — a rule whose examples are all one domain gets looked past

dated evidence, from this rule's own `.see also`, 2026-07-28:

> `rule.require.reach-a-grove-through-its-duct` — this rule, specialized to groves. **split out
> 2026-07-28 because every example here is `aws`, and a reader looked straight past it while they
> typed `ssh grove-1`.**

that is a general **authoring** lesson about rules, and the learner is exactly the role that owns
it:

> a rule whose every example draws from one domain will be read as a rule *about* that domain.
> when a reader violates it in a second domain, the repair is not a louder `.what` — it is a
> **named specialization** in the domain they were standing in.

candidate name: `rule.require.specialize-a-rule-its-readers-look-past`. its evidence is already
two-deep in this repo (aws → groves), and the pattern will recur every time a general rule meets
a second domain.

### 5. the skill-shape contract deserves a template artifact

the rule's `.how` lists five things a skill owes:

1. `--env` whose credentials come from keyrack
2. the active account/identity reported **before** any result
3. tree-struct output
4. errors that name the fix, not the symptom
5. a `.what` / `.why` header, and a `guarantee` block that says read-only when it is

five requirements in prose is a checklist nobody diffs against. `domain.terms/` already proved the
better shape — `template.domain-term.md`, a concrete skeleton to copy. the same move applies:
`template.wrapped-cli-skill.sh`, so the contract is satisfied by construction rather than by
recall.

### 6. the `guarantee` block, and read-only as a first-class claim

item 5 above smuggles in something worth its own line. a skill that declares

```
# guarantee:
#   - READ-ONLY with respect to the repo; writes only under temp dirs it makes, and removes both
```

has told a human what it *cannot* do, which is what makes it allowlistable without a read. that is
the mechanism by which a wrapped call becomes cheaper to approve than a raw one — and it is the
economic argument for the whole rule.

## ⚠️ .the counter-evidence the brief must carry

**the rule was in context, and it did not hold.** this is the most useful thing this session
produced, and a brief that omits it would be dishonest:

> on 2026-07-29, in a session where `rule.require.wrap-cli-in-skills` **and** its grove
> specialization were both booted into context and had been read aloud, a robot ran raw
> `ssh grove-1` roughly **ten times in one hour**. the human had to ask: *"why do you need direct
> ssh grove-1 ever?"* and *"why cant you always use ducts with --play files"*.

the friction was mundane — a duct was busy, and raw ssh was one keystroke closer. the rule lost to
convenience despite being read, believed, and agreed with.

so the crystallization must not stop at a brief. per
`rule.always.externalize.tactics.into_skills`, the enforcement has to be **encoded**:

| layer | artifact | what it catches |
|-------|----------|-----------------|
| knowledge | the brief | a traveler who has not met the lesson |
| **mechanism** | a preToolUse hook that rejects a bare wrappable invocation and names the skill | a traveler who **has** met the lesson and is in a hurry |

the second row is the one this session proves is required. the allowlist already blocks *unknown*
commands; what it does not do is block a **known-but-wrappable** one (`ssh grove-1` is
prefix-allowed) while it points at the skill that should have carried it. that hook is the missing
mechanism, and its error message writes itself:

```
✋ raw `ssh grove-1` — this belongs in a skill
   └─ fix: rhx git.grove.send grove-1 --what '<cmd>'
      why: rule.require.reach-a-grove-through-its-duct
```

## .what the brief should carry

1. **the claim**, generalized past "external CLI" per candidate 1
2. **the two arguments** — the practice argument (reviewable, repeatable, loud) and the
   **mechanism** argument (the outer string is the unit of trust), stated as peers. the second is
   what makes a robot act, and today it is a buried paragraph
3. **the four wrappable kinds** — external CLI, remote reach, local play, flag incantation
4. **the unnameable-guard invariant** (candidate 2), with the three-credited-fixes evidence
5. **the specialization pattern** (candidate 4), with its aws → grove precedent
6. **the counter-evidence** — that the rule was read and still lost, and therefore the
   accompanying mechanism is not optional
7. **the skill-shape template** as an artifact, not a list (candidates 5, 6)
