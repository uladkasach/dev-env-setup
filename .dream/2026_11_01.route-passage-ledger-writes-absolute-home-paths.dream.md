# 🌙 dream: the route passage ledger records each review by its ABSOLUTE path, home dir and all

- kind: reseed
- owner: ehmpathy/rhachet-roles-bhrain (role=driver, `route.stone.set`)
- caught 2026-11-01

## .the cue that fired

the done-gate commit for `v2026_10_23.fix-grove-crew-users-linger` staged
`.route/passage.jsonl`, and a dox scan of it matched an absolute home path on every
concession and dispute row. the director ruled it an upstream defect: catch it, do not patch
it here.

## .the gap, precisely

`rhx route.stone.set --as conceded|disputed … ` appends a row whose `given` field is the
review file's ABSOLUTE path:

```json
{"stone":"1.vision","status":"conceded","reviewer":"<reviewer>","about":"blocker.1",
 "given":"/home/<user>/git/<org>/_worktrees/<repo>.<branch>/.behavior/<route>/.reviews/peer/<file>.md",
 "severity":"better","reason":"…"}
```

- the ledger is a tracked route artifact, so every route that commits it publishes the seat's
  home dir, its user name, and its worktree layout. in a public repo that is dox
  (`rule.forbid.dox-in-public-repo`)
- the path is also wrong on any other clone: the same review sits at a different absolute path
  there, so the field cannot be followed by the next reader anyway
- the route's crash logs (`.malfunctions/*.crash.*.log`) carry the same absolute route path,
  plus the driver session id. this repo now gitignores those; the ledger it must still commit

## .the shape of the fix

- write `given` relative to the route dir (`.reviews/peer/<file>.md`), which is all a reader
  needs and is the same on every clone
- read old rows tolerantly: an absolute `given` that sits under the route dir is reduced to the
  relative form on read, so a ledger that mixes both still resolves
- a clamp: a test that sets the route under a fixture `$HOME` and asserts no ledger row
  contains that `$HOME`
- the crash log's `route:` line wants the same relative form, and its `clone:` id only where a
  reader acts on it

## .why it is not done in this round

the writer is a package this repo consumes and does not own; a patch to the installed copy
would be lost on the next `pnpm install` and leave every other repo exposed. it is a reseed,
dispatched to its owner. the rows already in this branch's ledger stay as written; a rewrite of
them is the owner's fix applied, never a hand edit of the ledger.
