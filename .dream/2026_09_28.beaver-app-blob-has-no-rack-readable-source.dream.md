# 🌙 dream: the BEAVER app blob cannot be forwarded, because the rack mints from it rather than returns it

- kind   = reseed
- owner  = a human — a paste is STRUCTURALLY required, not merely convenient
- caught = 2026-09-28

## .the cue that fired

two claims, identical on both seats of `grove-ahbode-v20260811`, and the only rows left between
that box and a green gate:

```
✋ ahbode.prep.EHMPATH_BEAVER_GITHUB_TOKEN — the rack hands over an EMPTY value
✋ ehmpathy.prep.EHMPATH_BEAVER_GITHUB_TOKEN — the rack hands over an EMPTY value
```

⚠️ **`EMPTY` is its own state, beside `absent 🫧` and `locked 🔒`** — and it is the one that most
invites a wrong repair, because an entry plainly exists.

## .the gap, precisely

the same two slugs read a **real token** from this laptop, one minute earlier. so the value is not
absent from the world; it is absent from the GROVE. the obvious cure is the forward hop
`rule.require.github-token-at-all-camp` describes — *"the FILE cannot travel; the VALUE can"* —
and that hop is refused:

```
$ rhx git.grove.auth.keys.set grove-ahbode-v20260811 --mode plan
✋ ahbode.prep.EHMPATH_BEAVER_GITHUB_TOKEN — mech is EPHEMERAL_VIA_GITHUB_APP,
   and only PERMANENT_VIA_REPLICA can be placed
```

🔴 **and the refusal is correct, for a reason no flag can route around.** per
`gotcha.github-auth-two-paths.demo=keyrack-mint-and-org-gap`, m1, this mech stores a blob of
`appId` + `privateKey` + `installationId` and **mints** an installation token from it on every
read. so:

| what a `get` returns | what a forward hop would need |
|---|---|
| a freshly minted `ghs_…`, valid ~55 min | the permanent blob the mint reads FROM |

⇒ **the rack has no verb that returns the blob.** a pipe can only carry what a `get` emits, and a
`get` emits the mint's output. the source is reachable only past the rack, in the age-encrypted
`os.secure` file — which `rule.require.reach-credentials-through-keyrack` forbids outright.

## .why it is not done in this round

it is not deferred for size or dirt. **no driver-owned command exists.** the cure the tool itself
prints is to file the blob centrally, and a blob has exactly one source a machine can offer it
from: a human who holds it.

```sh
rhx keyrack set --owner ehmpath --key EHMPATH_BEAVER_GITHUB_TOKEN \
  --org ahbode   --env prep --mech EPHEMERAL_VIA_GITHUB_APP --vault aws.params
rhx keyrack set --owner ehmpath --key EHMPATH_BEAVER_GITHUB_TOKEN \
  --org ehmpathy --env prep --mech EPHEMERAL_VIA_GITHUB_APP --vault aws.params
```

🛑 **HERE, on the laptop, never on the grove.** a `set` prompts, a prompt wants a tty, and a tty on
the provision path is a blocker that also wedges the duct
(`rule.forbid.tty-as-a-proxy-for-a-human`, `rule.require.one-command-provision`).

⚠️ and `--vault aws.params` is the load-bear half: `aws.params` is CENTRAL, so one write serves
every grove and each box mints its own token thereafter. `os.secure` is a replica — it would need
the same paste per box, forever.

## ✔ .the rack was READ — measured 2026-09-29, so the ask is now the paste ALONE

step 2 below asked for a read before any write. that read is a driver's, and it is done:

```
├─ ahbode.prep.EHMPATH_BEAVER_GITHUB_TOKEN
│  ├─ mech: EPHEMERAL_VIA_GITHUB_APP
│  └─ vault: os.secure
├─ ehmpathy.prep.EHMPATH_BEAVER_GITHUB_TOKEN
│  ├─ mech: EPHEMERAL_VIA_GITHUB_APP
│  └─ vault: os.secure
```

🔴 **both rows sit at `os.secure`, and that is the CAUSE of the EMPTY, not a detail beside it.**
`os.secure` is a REPLICA vault — each box holds its own age-encrypted copy — so a fresh grove has
no copy to read, and reads EMPTY forever however healthy the laptop's own copy is
(`rule.require.github-token-at-all-camp` states the replica hazard by name).

⇒ so `--vault aws.params` in the two commands above is a **vault MOVE**, never a fill of a blank:

| | today | after the paste |
|---|---|---|
| where the blob lives | `os.secure`, one copy per box | `aws.params`, one central copy |
| what a fresh grove reads | ✋ EMPTY — it holds no replica | ✔ the blob, minted per read |
| what a rotation costs | a paste per box, forever | one write |

⚠️ and the move is what makes the paste worth a human's minute. a paste that kept `os.secure`
would clear these two claims on THIS laptop and on no grove at all.

🟡 one peer row sits beside them and is NOT one of the two: `ehmpathy.prep.BEAVER_APP`, same mech,
same vault. whether the two token rows read that blob or hold their own is unread — it changes no
step below, and it is the first place to look if the paste does not clear the claims.

## .the shape of the fix

1. the human runs the two `keyrack set` lines above, on the laptop, and pastes the app blob at
   each prompt
2. ✔ **the rack is read** — see the measurement above. `set` has no entry-only mode, so it
   OVERWRITES whatever is live at that slug; what is live is `os.secure`, and the write moves it
3. then the grove needs no paste at all: `rhx git.grove.provision boot <grove> --mode apply --from 2`

## .what this dream does NOT claim

it does not claim the tool is wrong. `git.grove.auth.keys.set` refuses precisely because a minted
token would expire ~55 minutes after it landed, so the grove would pass its gate today and fail it
before lunch — a far worse outcome than the honest refusal.

⇒ so the absent capability is *"file an app blob with no human"*, and that may be unbuildable: the
blob is a credential no machine in this system is entitled to read.
