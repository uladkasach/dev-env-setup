# 🌙 dream: a pnpm patch that fails to apply fails the install

- kind: fix
- owner: this repo, `package.json` + `pnpm.modules.sync`
- caught 2026-11-23

## .the cue that fired

the `rhachet-roles-ehmpathy@1.43.0` patch failed four times with `ERR_PNPM_PATCH_FAILED`.
it failed loud only because this tree's uncommitted `package.json` lacked main's
`"ignorePatchFailures": true`. on main's pins, the same failure would be a mere warn, and the
verb would run unpatched with no signal.

## .the gap, precisely

main's `package.json` sets `allowUnusedPatches` and `ignorePatchFailures` to true. a patch
that cannot apply lets the install pass, and the patched behavior silently drops away. today
the only detector is a clamp per patch: `prove.git-commit-push-as-human-asks-gh-at-the-push`
for the ehmpathy patch, and `prove.guard-reruns-a-lane-whose-latest-given-refused` for bhrain.

## .the shape of the fix

drop `ignorePatchFailures` (and `allowUnusedPatches` once no stale entry is left), so a patch
that fails to apply fails the install. before that, find out why main set it: was it the same
read-only file mode that blocked the ehmpathy patch? then prove `pnpm.modules.sync --mode apply`
goes red on a broken patch and green on main's two.

## .why it is not done in this round

it changes how every install on every seat treats patches, beyond the push cure in #213. #213
also waits on a review of its current head, so a further commit there would move the head
that review reads.
