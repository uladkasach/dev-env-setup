## .the ask, as the human framed it

> then the bhuild superviser can simply leverage unix.duct and unix.term for its grove skills

> target grove is local or cloud hosted

## .the composition, in one line

```
playwright  ──produces──▶  a .play.sh for unix.duct / unix.term
supervisor  ──consumes──▶  by NAME only, and holds no duct knowledge at all
```

the **play file is the seam**. it is the only artifact that crosses between the two roles, and that
is what makes each one's boundary honest:

| role | owns | must NOT know |
|---|---|---|
| **playwright** | the *how* — how to drive a terminal surface, wait without a `sleep`, read without a race | what the work is for |
| **supervisor** | the *what* — which work, on which grove, in which order | ssh, tmux, a pane id, or whether the grove is remote |

## .why ONE interface, regardless of local or cloud

this is the load-bear claim, and `dev-env-setup` has already paid for both halves of it.

### the grammar already erases the distinction

its `duct.uri` uses an **empty authority** for a local duct, on the `file:///` precedent:

```
duct://grove-1/main/mechanic     # a duct on a remote grove
duct:///main/mechanic            # a duct on THIS machine
```

so "local or cloud" is a *value in one field*, not a fork in the code. a supervisor that branches
on it has re-introduced a distinction the grammar exists to remove.

### two interfaces would be two lists, and this repo has retired two already

| the two lists | how they drifted | what retired them |
|---|---|---|
| `install_env.sh` + `install_env.grove.sh` | a fix landed in one, absent from the other; neither could be trusted as the record | one list, each entry tagged `any`/`local`/`cloud` |
| `git.grove.push`'s rsync + tar carriers | the two disagreed on WHERE content lands; one wrote a `src/src/` shadow copy and reported success | a layout check that drives BOTH, plus an explicit `--via` |

a `supervise.local` beside a `supervise.cloud` is the same shape as the first row, and it would
drift the same way. the `--for local|cloud` tag is the proven answer: **one list, each entry
declares where it belongs.**

> the supervisor does not need to know where a grove lives. it needs to name what it wants done
> there.

### the local case is not a special case; it is the CHEAP case

worth a plain statement, because the instinct runs the other way. a local grove is not a degenerate
remote — it is the same surface reached with a shorter wire. every argument for a duct (durable,
reattachable, survives a dropped client, holds its cwd across a reboot of the held program) is
just as true on the laptop. this session used a *local* duct to drive a *remote* one.

## .what the supervisor should be able to say

the whole vocabulary, with no transport in it:

```sh
# the supervisor's grove skills, expressed as plays it names
rhx grove.supervise --on 'duct://grove-1/main/mechanic' --play grove.provision
rhx grove.supervise --on 'duct:///main/mechanic'        --play grove.provision   # same call, local
rhx grove.observe   --on 'duct://grove-1/main/*'                                # read-only
rhx grove.repair    --on 'duct://grove-1/main/mechanic' --rung reboot
```

not one of those lines mentions ssh, tmux, a pane, or a host key. that absence is the deliverable.

### the repair ladder must be a supervisor concept, not a hidden one

`dev-env-setup` learned this the hard way and wrote the ladder down, ordered by cost:

```
duct.refresh   free       repaint the client; kills not one program
duct.reboot    cheap      kill the HELD program; the session and its cwd survive
duct.stop      expensive  kill the session itself
```

a supervisor that can only `stop` will `stop` — and lose a session to fix a repaint. so the ladder
is part of the interface, with its ORDER visible. `--rung refresh|reboot|stop` names it, and the
cheapest rung that could work is the one a supervisor should reach for first.

## ⚠️ .the failure mode this composition exists to prevent

stated with its evidence, because the argument is empirical and not aesthetic.

> on 2026-07-29, in a session where `rule.require.reach-a-grove-through-its-duct` was booted into
> context **and had been read aloud**, a robot ran raw `ssh grove-1` roughly **ten times in one
> hour**. the human had to ask: *"why do you need direct ssh grove-1 ever?"* and *"why cant you
> always use ducts with --play files"*.
>
> the friction was mundane: a duct was busy, and raw ssh was one keystroke closer. the rule was
> read, believed, agreed with, and lost to convenience.

the lesson is `rule.prefer.prevent-over-correct`: a **constraint** holds for every driver every
time; a **rule** relies on the driver to remember it while in a hurry.

so the composition is the constraint. a supervisor whose only vocabulary is *play names* cannot
reach for ssh — the capability is **absent**, not merely discouraged. that is a stronger guarantee
than any brief, and it is the real argument for the split.

### and it composes with the escalation meter

the peer dream proposes `unix.uses` (modeled on `radio.uses`: global / org / local, default
blocked, reads free, writes granted). a supervisor sits naturally inside it:

| what the supervisor does | needs |
|---|---|
| `grove.observe` — list, read | free (read-only) |
| `grove.supervise` — send a play | granted |
| `grove.repair --rung reboot|stop` | granted |

so a supervisor can *always* observe and *never* act unbidden. that is the same line
`git.commit.uses` draws between `stage` and `push`, and it means an unauthorized supervisor is
still useful rather than inert.

## .what the dispatch should deliver

1. **the composition, named** — playwright produces plays, supervisor consumes them by name; the

2. **`rule.require.one-grove-interface`** — a supervisor reaches every grove through

6. **the prevent-over-correct argument** — with the ten-raw-ssh-calls-in-one-hour evidence, so a
   future reader knows the constraint was bought, not preferred

## .the open question worth a flag

does a supervisor ever need `unix.term` at all?

- **`unix.duct`** — plainly yes. that is where work runs
- **`unix.term`** — the frame a *human* looks at: windows, tabs, focus. a supervisor arranges work,
  not eyeballs

the honest guess: a supervisor needs `unix.term` only to *present* — to put the right duct in front
of a human when it needs attention. that is a real need (this repo's `termwork` briefs are exactly
about role-tabs and window management) but it is a **narrow** one, and it should be argued
explicitly rather than granted by symmetry with `unix.duct`.

flagged rather than decided, per `rule.always.defer-fulcrums-to-last`: it is a clean rework either
way, so it should not hold the dispatch.
