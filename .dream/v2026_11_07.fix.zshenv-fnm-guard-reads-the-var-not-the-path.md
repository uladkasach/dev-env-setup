# 🌙 dream: the zshenv nested-shell fnm guard reads the var, never the PATH entry

- kind: fix
- owner: dev-env-setup
- caught 2026-11-07

## .the cue that fired

`rhx play.run --all --within 900`, run `2026-11-07T17-22-07Z`: `prove.rc-is-quiet-on-boot` arm 0b
→ an interactive zsh wrote fnm's `The current Node.js path is not on your PATH` to stderr at boot.
the play's own read: a fresh boot with `FNM_MULTISHELL_PATH` scrubbed is quiet.

## .the gap, precisely

a parent that exports `FNM_MULTISHELL_PATH` without its bin dir on `PATH` makes every child zsh
skip the `fnm env` eval (`2.5.zsh/zshenv.sh`, the nested-shell guard), so the child boots with a
node path fnm itself calls broken. an agent harness is such a parent.

## .the shape of the fix

the guard skips the eval only when `$FNM_MULTISHELL_PATH/bin` is already a `PATH` entry, never on
the var alone. then rerun `prove.rc-is-quiet-on-boot` from the harness shell, and plan / apply /
apply `2.5.zsh` on a grove.

## .why it is not done in this round

a shell-rc bundle change, outside the play.run wish; its proof is a bundle run on a grove.
