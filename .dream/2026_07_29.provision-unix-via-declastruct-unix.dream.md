dream = provision unix machines via `declastruct-unix`

## .what

replace this repo's hand-rolled bash convergence with a **declastruct** provider for unix —
`declastruct-unix` — so a machine's state is a set of **declared resources** with `get` + `set`
semantics, rather than shell phases that each hand-roll their own convergence.

⚠️ **premise updated 2026-07-31.** this dream was drafted 2026-07-29 against the OLD
`src/install_env.pt*.sh` stepfn driver (~60 `install_*`/`configure_*` functions driven by a
`step <tag> <fn>` inventory). that driver was DELETED in the 2026-07-30 hard cut and replaced by the
`src/grove.provision/` BUNDLE tree — 43 leaves that carry phases, each with up to four
`{provision,configure}.{upsert,verify}` phases (`readme` + `rule.require.bundle-as-sole-declaration`).
so the target this dream replaces is now the BUNDLE framework, and the whole catalog below is itemized
from those 43 leaves, not the deleted stepfns. the migration bridge is direct: a leaf's
`configure.verify.sh` is already a `get`, its `configure.upsert.sh` a write-only `set` (see the
escape-hatch section).

the dream: each declared bundle becomes a declastruct resource.

a tree is authored as a **wish** — a flat list of DECLARED resources, refs by `exid`, in
dependency order. the author declares desired state; the engine reads live state and reconciles it
(plan → apply). this mirrors `declastruct-aws` exactly
(`provision/aws.infra/account=demo/resources.ts` + `resources.vpc.ts`), where a `DeclaredAwsVpc.as({
exid, cidr, … })` is declared and a subnet refs it by `{ exid: vpc.exid }`. the author never calls
`set*` by hand — there is no imperative path to forget on.

```ts
// a resource group: declare desired state, ref siblings by exid (like aws subnet -> vpc)
export const getResourcesOfShell = (): DomainEntity<any>[] => {
  const zsh = DeclaredUnixPackageViaApt.as({ exid: 'pkg-apt-zsh', package: 'zsh' });
  const zshrc = DeclaredUnixFile.as({ exid: 'file-home-zshrc', path: '~/.zshrc', from: 'src/zshrc.sh' });
  const loginShell = DeclaredUnixLoginShell.as({
    exid: 'loginshell-camper',
    user: 'camper',
    shell: { exid: zsh.exid }, // ref by exid — the engine orders zsh before the login shell
  });
  return [zsh, zshrc, loginShell];
};

// resources.ts aggregates every group into ONE flat wish, in dependency order
export const getProviders = async (): Promise<DeclastructProvider[]> =>
  [await getDeclastructUnixProvider({}, { log })];
export const getResources = async (): Promise<DomainEntity<any>[]> => [
  ...getResourcesOfSystem(),
  ...getResourcesOfShell(),
  ...getResourcesOfTerminal(),
  // … one group per composite; the whole tree is one declared set
];
```

```bash
# apply is the engine's job, not the author's — same two verbs as aws.infra
npx declastruct plan  --wish provision/unix/resources.ts --into .temp/plan.json
npx declastruct apply --plan .temp/plan.json
```

the engine invokes `getUnix$X` then `setUnix$X({ findsert | upsert })` per resource as it
reconciles the wish; those set-ops are the provider's internals, NOT the author's surface.

## .why

### idempotency stops being a per-step promise

`rule.require.grove-provision-as-the-only-entrypoint` makes every entry in the inventory owe
convergence, and `rule.require.idempotent-install-procedures` lists the shapes that satisfy it.
but the obligation falls on the AUTHOR of each of the 43 leaves' phases, every time, forever — and
the enforcement is a code review plus a re-run.

declastruct's `get`/`set` contract makes convergence structural: a `set` with `upsert` is
idempotent by construction, because the provider reads current state before it writes. the
author cannot forget, because there is no imperative path left to forget on.

that is the same argument the ehmpathy canon already makes at
`rule.require.fewer-paths-via-idempotency`: do not guard around an unsafe operation — make the
operation safe, then delete the guard. every `[[ -f x ]] ||` and `grep -q … ||` in the bundle
`*.upsert.sh` phases is such a guard.

### the four duplicate-driver incidents were all list drift

`install_env.grove.sh`, `grove.provision.grove`, the slice suite, and the skill's own 7-file
array — each was a second LIST of what a machine gets. a declared resource set has no second
list to grow: `--for cloud|local` becomes a filter over declared resources, not a hand-kept
subset.

### a plan becomes a real diff, not a roll of names

`--mode plan` today prints the step names it WOULD call. a declastruct plan can print the
**state delta** — what is already converged, what would change, and what the change is. that is
the difference between "i would call install_zsh" and "zsh 5.9 is present; no change".

### EXTEND the extant patterns — do NOT invent a new shape

`declastruct-unix` is a NEW provider, but it is NOT a new pattern. it EXTENDS three repos that
already exist. copy their shapes; do not reinvent them. a unix box is a repository of resources
like any api is, so the same three layers apply unchanged:

1. **`ehmpathy/declastruct` (the core) — the reconcile seam.** extend this, do not reimplement it.
   every `DeclaredUnix*` is a `DeclaredResource<T>`, which IS a `DomainEntity<T>`. every DAO is a
   `DeclastructDao` built by `genDeclastructDao`. change is decided by the core's `computeChange`
   — `serialize(omitReadonly(remote)) === serialize(omitReadonly(desired))` → KEEP/CREATE/UPDATE/
   DESTROY. the whole `DeclaredUnixImperative` escape hatch below is designed to plug into THIS
   seam (the `method` field is `readonly` precisely so `omitReadonly` strips it before the compare).

2. **`ehmpathy/declastruct-aws` `provision/aws.infra/` — the wish layer.** extend how it composes a
   plan. one `getResourcesOf$Subject()` per subject, each yielding a flat `DomainEntity[]`; a top
   `getResources()` concatenates them. resources are cast with `Declared$X.as({ exid, … })` and
   refer to each other by `{ exid }`, never by nested object. drive it with the same cli:
   `npx declastruct plan --wish … --into …` then `apply --plan …`. its self-provision acceptance
   test — a wish that stands up its own arrange state — is the test model to copy too.

3. **`ehmpathy/declastruct-unix-network` — how a unix resource is written, AND resources to REUSE.**
   this is the closest precedent: a peer unix provider in the same org. extend how it declares a
   dobj (a `DomainEntity` with `static unique` + `static readonly`) and pairs it with a
   `genDeclastructDao` DAO that delegates to `getOne*` / `set*` / `del*` over `osUnix*` sdks, with
   `set.upsert = null` as the never-clobber. and it ALREADY BUILDS resources this provider needs —
   `DeclaredUnixSshKeypair`, `DeclaredUnixHostAlias`, `DeclaredUnixPortAlias`, `DeclaredUnixSshAlias`,
   `UnixEndpoint`. REUSE those; do not re-author them. the plan is to pull `-network` INTO `-unix`
   proper eventually, so `-unix` should depend on it and follow its shape exactly.

`rule.prefer.declastruct.[demo].md` carries the full worked pattern end to end: declare the entity,
cast sdk↔domain, `get` by primary/unique/ref, `set` by findsert/upsert.

#### the install family — `Package` vs `Binary`, and `Via$Slug`

the earlier draft had one `UnixPackage` type. that is WRONG on the corpus and on the contract. what
Linux prose actually calls "the unit you install" splits two ways, and so does the `get`/`set`:

- **`package`** — the word every manager uses (apt/dpkg/rpm/pacman/npm). a MANAGER tracks it:
  queryable, cleanly removable. ~30 of the installs.
- **`binary`** — the `/usr/bin` word for a hand-placed artifact. NO manager: you fetch, verify a
  checksum, place it, and parse its own `--version`. ~9 installs (starship, kitty, nvim, usql, aws,
  ssm, fnm, rustup-installer).

the split is not taste — it falls on a contract-SHAPE boundary:

| the managed vias | the binary via |
|------------------|----------------|
| `get` = ask a manager (`dpkg -s` · `flatpak info` · `pnpm ls -g`) | `get` = stat the path + parse `--version` yourself |
| `set` = tell a manager (`apt install` · `flatpak install` · `pnpm add -g`) | `set` = curl + sha256 + place + chmod |
| `del` = manager removes cleanly | `del` = `rm` (no manager to consult) |

managed-vs-unmanaged is a contract-SHAPE boundary → a TYPE split.
apt-vs-flatpak-vs-pnpm is only a COMMAND boundary → it would be a field WITHIN package…

…EXCEPT the unique KEY namespace differs per via, which forces separate classes, not a field:

| class | tier | unique key (its namespace) | `get` |
|-------|------|-----------------------------|-------|
| `DeclaredUnixPackageViaApt` | A | apt package name (`ripgrep`, `docker-ce`) + optional `repo` | `dpkg -s` |
| `DeclaredUnixPackageViaFlatpak` | A | flatpak app-id (`org.mozilla.firefox`) | `flatpak info` |
| `DeclaredUnixPackageViaPnpm` | A | npm package name (`@anthropic-ai/claude-code`) | `pnpm ls -g` |
| `DeclaredUnixPackageViaCargo` | A | crate name (`tree-sitter-cli`) | `cargo install --list` |
| `DeclaredUnixBinary` | B | install path (`~/.local/bin/starship`) + `install: PickOne<{ tarball: {url; sha256}; installer: {url} }>` | per-tool `--version` (+ checksum for tarball) |

`ripgrep`, `org.mozilla.firefox`, and `@anthropic-ai/claude-code` are three DIFFERENT namespaces —
not one `name` field with a `via` tag. a shared `name` would carry a different sense per arm: the
overload trap, in the IDENTITY field itself. so each via is its own `DomainEntity` with its own
`unique` and its own `get`. a `DeclaredUnixPackage` INTERFACE (not a base class) carries the family
shape — `version`, the presence contract — that the three `Via$Slug` classes `implements`, so `plan`
can iterate a known family without a class hierarchy.

- **`via.apt.repo` folds the source into a field — BUT the 2026-07-31 audit REOPENED this.** the
  original call: gh/docker/codium/protonvpn are `PackageViaApt` with a declared `repo` field, so a
  separate `UnixAptRepo` type is unneeded. that holds while a vendor repo serves exactly ONE package
  (docker.list → docker). it BREAKS on two cases the audit surfaced: (1) the **flathub remote** is
  shared by 5 flatpaks (`1.3.1.firefox`, `4.2.ptyxis`, `6.1.flatpaks`×3) — a per-package field would
  declare the same remote 5×, so it MUST be one shared `PackageSourceViaFlatpakRemote` the packages ref by
  exid (exactly the aws subnet→vpc pattern); and (2) a **PPA** (`1.1.keybinds`) or a shared apt
  source can serve several packages likewise. so the audit re-adds a `PackageSourceVia{Apt,
  FlatpakRemote}` family (see the part-2 summary table; apt's ppa is a `PickOne` sub-shape of
  `ViaApt`, not its own class): a source is its own resource, ref'd by the
  packages that need it, NOT a field duplicated per package. the field-fold survives ONLY as an
  optimization for the strict 1:1 vendor-repo case.
- **`Via$Slug` is on the CLASS and its mechanisms** — `DeclaredUnixPackageViaApt`,
  `setUnixPackageViaApt`, `getUnixPackageViaApt`. `filename===opname` (rule.require.sync-filename-opname).
- **the honest cost** — a tool's TYPE is a function of its DELIVERY. nvim-via-binary is a
  `DeclaredUnixBinary`; move nvim to apt and it becomes a `DeclaredUnixPackageViaApt` — a
  delete-and-recreate across classes, not a field edit. and there is no single "is nvim present?"
  query across delivery. this is correct HERE because every raw-binary leaf PINS deliberately —
  delivery is a declared choice worth a loud type — but note that a delivery migration is a type
  change.
- **the runtime seam settles under the split** — `manager`-via (node/tf/rust) is NOT a fourth
  package arm. the managers THEMSELVES (fnm/tfenv/rustup) are `DeclaredUnixBinary`; the runtime is
  its own `DeclaredUnixRuntime { manager; version }` that COMPOSES that binary plus a
  version-selection. the split made this plain; a unified type would have buried it in a union arm.

#### the file family — three OWNERSHIP tiers

a file resource splits on ONE question: how much of the file do we own? FOUR answers, four types,
each with a distinct unique key and a distinct SAFETY guarantee:

| type | unique key | owns | set | on re-run | the file is |
|------|-----------|------|-----|-----------|-------------|
| `DeclaredUnixFile` | `path` | the WHOLE file | write all content from repo | overwrites to declared | ours top-to-bottom (`~/.zshrc`, ptyxis keyfile, claude settings.json, codium product.json, ~8 COSMIC files) |
| `DeclaredUnixFileBlock` | `path` + `marker` | a FENCED region | replace between the fences; leave the rest | re-renders the region (2→3 lines cleanly) | shared (`~/.profile`, terminfo rc) |
| `DeclaredUnixFileLine` | `path` + `line` | one EXACT line | ensure the line is present | finds it → no-op | shared (`/etc/fstab`, `known_hosts`) |
| `DeclaredUnixFilePatch` | `path` | a PATCH (edits) over a vendor source | re-patch: read the system source, apply declared substitutions, write | re-applies substitutions to the CURRENT source | a system file we hold an OPINION about (`system_actions`) |

the ownership ladder, from most to least owned:

- `File` — we own the whole file. write it. FORMAT IS IRRELEVANT (INI, json, ron, keyfile — all
  `File` when we write them whole). the biggest tier by far: ptyxis, codium, claude, most of COSMIC.
- `FileBlock` — a marker (`# >>> grove:fnm >>>` … `# <<<`) fences OUR region in a shared file; the
  content inside is MUTABLE, so `set` re-renders it. correct for an evolving hook. the terminfo leaf
  already hand-rolls exactly this ("every marker this leaf has ever written, oldest first").
- `FileLine` — the line's TEXT is its identity; IMMUTABLE (change the text = a different line, old
  one orphans). correct for an fstab mount, a `known_hosts` entry — facts present or absent.
- `FilePatch` — we own NEITHER the file NOR a fixed region; we own a PATCH (a set of edits) over a
  vendor source that grows between releases. `set` reads `/usr/share/cosmic/.../system_actions`,
  applies the 5 declared `sed` rules, writes the user copy — so upstream additions flow through
  untouched. the `3.3.desktop` leaf's own header warns exactly why `File` is WRONG here: "to declare
  it whole would freeze this box at whatever table was current the day it was written."

  the word `patch` chosen over `derived`: `patch` names what we OWN (edits over a foreign base) and
  is the corpus word (`patch(1)`); `derived` names only the relationship and is vague (a symlink, a
  binary, a template all "derive"). forbidden synonyms: `derived`, `overlay` (implies a merged layer,
  not edits-over-base), `template` (renders from OUR source — wrong direction). caveat: strict
  `patch` = a unified diff; here we mean the BROAD sense (any edits over a base), with
  `substitutions: [{ match, replace }]` as the representation — a unified-diff base could later join
  the same type.

honest instance counts TODAY:
- `File` — the large majority (all whole-file writes, any format)
- `FileBlock` — 2 (`~/.profile` fnm hook, terminfo erase region); both were mis-called "line" earlier
- `FilePatch` — 1 (`system_actions`)
- `FileLine` — 0 with an instance; its natural home (the fstab swap line) is currently owned inside
  `DeclaredUnixSwapfile`'s bespoke logic. DECLARED for the immutable-fact case it will serve.

**one verify ⇒ a composite resource; many independent verifies ⇒ a group function.**

#### the generic escape hatch — `DeclaredUnixImperative`, the ur-primitive every named type derives from

the whole named taxonomy above is a CONVENIENCE layer. underneath, the declastruct engine does
exactly ONE thing, for every resource alike. ✅ **VERIFIED against the declastruct core, 2026-07-31**
(`ehmpathy/declastruct` `src/domain.objects/{DeclaredResource,DeclastructDao,DeclastructChange}.ts` +
`src/domain.operations/plan/computeChange.ts`) — the design survives, with three corrections below.

the real contract (not my earlier paraphrase):
- a `DeclaredResource<T>` is literally `DomainEntity<T>` — exid/unique/primary, and no more.
- a `DeclastructDao` is `{ get.one.byUnique|byPrimary|byRef(ref,ctx) → Instance|null ; set.findsert|upsert?|delete?(input,ctx) }`.
- `computeChange({ desired, remote })` derives the action by a SERIALIZED deep-equal:

```ts
// computeChange.ts — the actual engine seam
if (!remote)  return CREATE;                 // get returned null
if (!desired) return DESTROY;                // desired: null  → dao.set.delete
areEquivalent = serialize(omitReadonly(remote)) === serialize(omitReadonly(desired));
return areEquivalent ? KEEP : UPDATE;        // else dao.set.upsert
```

a NAMED type IS a `DeclastructDao` with get/set curated in TypeScript. the escape hatch lets the
DECLARATION inject them instead — a **dependency-injection escape hatch**, a generic DAO that reads
get/set off a `readonly method` field. folks use it like:

```ts
const installJq = DeclaredUnixImperative.as({
  status: 'done',                    // the DECLARED, compared attribute
  method: {                          // readonly ⇒ omitReadonly strips it BEFORE the serialize-compare
    get: () => isPresent('jq') ? { status: 'done' } : { status: 'todo', plan: { install: 'jq' } },
    set: () => { sh`sudo apt-get install -y jq`; },  // write-only converge, idempotent
  } /* as readonly */,
});
```

**correction 1 — the mechanism is `readonly`, and the core already has it.** i earlier called `method`
"write-only/transient". the exact declastruct word is **`readonly`**: `computeChange` compares
`serialize(omitReadonly(x))` on BOTH sides, so a `readonly method` (two closures that never compare
equal) is STRIPPED before the diff. so injecting get/set is invisible to the plan for free — no new
engine support, it is the `omitReadonly` that every resource already runs through. only `status`
diffs.

**correction 2 — the getter returns a RESOURCE INSTANCE, the engine verdicts, not the getter.** i
earlier wrote `get()` as if it emitted a `{status}|{status,plan}` VERDICT. the real `dao.get.one`
returns the live resource mirrored into the declared shape (`{ status }`), or `null`. the ENGINE
derives KEEP/CREATE/UPDATE by the serialize-compare above. so the `todo`/`done` is carried AS the
resource's `status` field: declared `{status:'done'}` vs a remote `get` that returns `{status:'done'}`
(→ KEEP) or `{status:'todo', plan}` (→ differs → UPDATE → `set` → re-get `{status:'done'}` → KEEP,
the fixed point). the `plan` rides on the remote instance as the legible diff. correct as designed —
just via the native serialize-compare, not a bespoke verdict.

**correction 3 — `del`/ensure-absent is NATIVE, not a "mode".** a removed package = a resource whose
`desired` is `null` → `computeChange` returns DESTROY → `dao.set.delete`. so `1.3.1.firefox`'s
`apt remove firefox` is just a declared resource with `desired: null`, no special casing.

**correction 4 — `skip` is NOT a native action; it rides the `status` field as a KEEP, or is an
omission from the env-wish.** the core's action enum is `KEEP | CREATE | UPDATE | DESTROY | REPLACE |
OMIT` — there is no `SKIP`. so the `status: skip|done` enum works only THROUGH the serialize-compare,
two clean ways:

| declared `status` | remote `status` (from get) | serialize-compare → action | effect |
|-------------------|----------------------------|----------------------------|--------|
| `done` | `done` | equal → KEEP | converged |
| `done` | `todo` (+ `plan`) | differ → UPDATE | `set` runs; plan printed |
| `skip` | `skip` | equal → KEEP | NO-OP — env out of scope, both agree |
| (omitted from wish) | — | — (never in plan) | NO-OP — filtered at `getResources` |

so `skip` is a resource whose declared AND remote `status` are both `skip` → KEEP → a no-op that is
still VISIBLE in the plan (better than silent omission). the messy cell (declared `done`, remote
`skip`) is an author error — do not declare `done` for a resource this env cannot hold; declare
`skip`, or filter it out of the wish. applicability thus has TWO honest homes, both native:
- **`getResources` filters by env** (the wish is env-specific — declastruct's own model) → the
  resource never enters the plan. this is the `--for cloud|local` filter, and it kills the
  four-duplicate-driver defect: one declared set, filtered, NOT a second list.
- **or a `status:'skip'` resource** stays in the plan as a legible KEEP (the repo's `🌙 declined`
  made visible), for when you WANT the plan to show "considered, skipped here".

either way it is NOT a bundle-level `[[ "$<OLD>_ENV_SERVER" != local@* ]]` guard hand-checked atop
every leaf — it is a wish-assembly filter or a declared status, both native to declastruct.

**the getter returns a resource STATE, the engine verdicts** — the generic DAO reads get/set off the
`readonly method`, in place of a provider-baked `getPackageViaApt`/`setPackageViaApt`, and hands the
result to the SAME `computeChange`:

```
declared = { status: 'done' }                 # the wish (readonly method stripped by omitReadonly)
remote   = dao.get.one.byUnique(ref)          # method.get() → { status: 'done' } | { status: 'todo', plan } | null
change   = computeChange({ desired, remote }) # !remote→CREATE ; serialize-eq→KEEP ; else→UPDATE
apply:     dao.set.upsert(desired) (=method.set); re-get → { status:'done' } → KEEP  (the fixed point)
```

`method.get` owns the diff (it alone knows the arbitrary API) but RETURNS state, not a verdict;
`method.set` is write-only and idempotent; the engine's `computeChange`, plan, apply, and fixed-point
check are all UNCHANGED. it "still works" because the escape hatch plugs into the get/set seam the
engine already has — the resource just INJECTS the DAO pair rather than the provider BAKES it.

**get/set take a CLOSURE or a declarative RUNNER — so folks never hand-write "exec this shell".** the
common case on unix is "run a `.sh` and read its output", so `method.get`/`method.set` accept a
runner descriptor as an alternative to a closure:

```ts
method: {
  // a runner is EITHER a file (uri) OR an inline command (cmd) — either is fine
  get: { run: 'shell', uri: 'src/.../jq.get.sh' },            // stdout = the { status, plan } JSON
  set: { run: 'shell', cmd: 'sudo apt-get install -y jq' },   // inline; exit 0 = converged (write-only)
}
```

a runner takes EITHER a `uri` (a `.sh` file, when the logic outgrows a line) OR a `cmd` (an inline
command, when it fits) — either is fine. the DAO execs it and reads the contract off the process:
the `get` runner's stdout MUST be the `{ status: 'done' } | { status: 'todo', plan }` JSON (a
non-zero exit = malfunction/constraint, per the repo's exit-code semantics); the `set` runner just
execs, exit 0 = converged, stdout/stderr are logs. so a get/set is a closure, a `.sh` path, or a
one-line command — never a hand-rolled `sh\`…\`` wrapper each time.

**this is also the MIGRATION BRIDGE.** the repo's CURRENT phase files already carry this shape:
`configure.verify.sh` is a `get` (it emits a verdict), `configure.upsert.sh` is a write-only `set`.
so each of the 43 leaves' phase pairs becomes the `{ run:'shell', uri }` get/set of a
`DeclaredUnixImperative` near-verbatim — the escape hatch is not a rewrite, it is the current bundle
phase-pair handed the declastruct get/set seam. named types are then carved out only where a granular
plan pays (below).

**named types are DERIVATIVES — you write one ONLY to buy a GRANULAR plan.** the sole thing a named
`DeclaredUnix*` adds is a get whose `todo.plan` is RICH STRUCTURED state, so the plan reads granular.
`DeclaredUnixPackageViaApt` through BOTH lenses — the SAME engine loop, only the plan's grain differs:

| | generic `Imperative` | named `PackageViaApt` |
|---|---|---|
| declared | `{ status: 'done' }` | `{ package: 'zsh', version: '5.9' }` |
| `get` | `dpkg-query`; absent/wrong → `{ status:'todo', plan:{ install:'zsh=5.9' } }` | `dpkg-query` → `{ version: '5.8' }` \| null |
| engine compare | `done ≠ todo` → apply | `5.8 ≠ 5.9` → update |
| plan reads | `todo: install zsh=5.9` (coarse) | `zsh: 5.8 → 5.9` (granular) |
| `set` | `apt-get install -y zsh=5.9` | `apt-get install -y zsh=5.9` |

both converge identically; the named one exists ONLY because `5.8 → 5.9` beats `todo: install
zsh=5.9` as a plan line. so:

> **the rule:** a custom `DeclaredUnix*` earns its keep ONLY when a granular plan is worth the code.
> otherwise escape-hatch to `DeclaredUnixImperative` — a `get` that reports done|todo+plan and a
> write-only `set`. every named type is a granular-plan SPECIALIZATION of the generic; the generic
> covers any unix-operable API we do not (yet) name. promote by wet-over-dry, once the grain pays.

##### when to reach for a named type vs `DeclaredUnixImperative` — the guidance

the etymology is the tell: **`Imperative` bridges imperative control → declarative control.** you
hand the engine an imperative get/set; it wraps them in declarative reconcile (plan/apply/fixed
point). the apparent oxymoron ("declared imperative") is the truth, not a defect — a DECLARED wrapper
(exid, `status`, engine-reconciled) around an IMPERATIVE `method`. the resource stays declarative:
`status` is compared, the engine reconciles; only the injected `method` is imperative. `Imperative`
names the escape hatch, NOT a bypass of the plan.

**the reach-for order:**

1. **a named `DeclaredUnix*`, IF one already covers it.** the named types are the paved road — use
   `PackageViaApt` for a package, `File` for a file. do NOT hand-roll an imperative where a
   declarative type already fits; that is a second, unvalidated way to do a solved thing — the exact
   drift this repo kills (`rule.require.repo-as-source-of-truth`).
2. **`DeclaredUnixImperative`, when it is NOT already supported.** an arbitrary unix-operable (but not
   unix-STANDARD) API with no named type — cosmic-import, a vendor CLI, a curl'd endpoint. the escape
   hatch is for the UNPAVED case, not the default.
3. **a good PROMOTION candidate = you want a granular plan OR the same imperative shape recurs 3+
   times.** keep it WET (`rule.prefer.wet-over-dry`): the first two uses of a shape stay
   `DeclaredUnixImperative`; the THIRD recurrence is a proven pattern worth a curated type. two uses
   is a coincidence; three is a pattern. and a granular plan is worth a name on its own, even at one
   use, IF `zsh: 5.8 → 5.9` reads better than the coarse `todo: install zsh=5.9`.

so the lifecycle: **named-if-supported → else Imperative → promote when the grain pays OR on the 3rd
recurrence.** a NEW capability is born `Imperative` (no type names it yet); an EXTANT one already has
its named road.

**the two things a named type buys** (why a promotion pays the code):
- a **granular plan** — `zsh: 5.8 → 5.9` beats the coarse `todo: install zsh=5.9`.
- a **stable identity others ref by exid** — a `PackageSourceViaApt`/flathub remote that 5 packages
  depend on MUST be a named node with an exid; a generic `Imperative` has no identity to ref. (this
  one can force a name BEFORE three uses — an escape hatch that others must point at is already owed a
  type.)

**NOT a trigger:** env-applicability. `skip` is handled uniformly by the `status` enum for both the
generic and every named type, so "this only runs on local" is NEVER a reason to promote — it is a
verdict, not a type.

**`ConfigViaCosmicImport` is DEFERRED (2026-07-31 decision): stay a `DeclaredUnixImperative` for now,
do NOT build `ConfigViaCosmic`.** it is the textbook first case for the escape hatch — a
unix-operable-but-not-unix-standard API, one use, no other resource refs it, and its `set`
(`cosmic-settings appearance import`) also DERIVES ~13 resolved keys + the GTK css from the 16 inputs,
so a per-key named store would be a partial model anyway. so: a `DeclaredUnixImperative` whose `get`
reads the readable per-key `~/.config/cosmic/…Dark.Builder/v1/*` store (the audit proved it is NOT
opaque) and reports `{status:'done'|'todo'}`, and whose `set` runs the import. it PROMOTES to a named
`ConfigViaCosmic` keyed store ONLY on the rule of three (a 2nd + 3rd cosmic-import resource) or if a
per-key granular plan (`accent: 5c8f… → desert-tan`) later proves worth the code — not now.

#### the noun, settled by the corpus (not `Program`/`Tool`)

earlier rounds circled `Program` then `Tool` as a genus above all delivery. the corpus check
("what does Linux prose call it?") ended that: Linux has NO genus word above `package`+`binary` —
it HAS `package` (managed) and `binary` (hand-placed), and names them separately. so we do too. the
rejected genus nouns, each with its reason, to record as forbidden synonyms when code lands:

- `Program` — OVERUSED; etymology (programma, "written before") names the CODE; 4 senses (source,
  process, tv-schedule, install)
- `Tool` / `Utility` / `Command` — the CLI cell only; surface is not a contract axis (see the
  decomposition below), so a surface-word cannot name the family
- `Application` — the GUI cell only
- a single `Package` that spans the binary via — false for the raw tarball; a tarball is not packaged

#### the decomposition that ruled surface out

three axes were walked against the 43 leaves: `via` (apt/flatpak/binary/pnpm/manager), `surface`
(CLI/GUI/daemon/toolchain), `managed?`. the test for "does an axis justify a separate resource" =
"does it split the `get`/`set` contract":

- **`via` splits the contract** — presence reads differently per via and only per via. the real axis.
- **`surface` does NOT** — `firefox present at v128` reads the same shape as `rg present at v14`;
  the read is via-shaped, surface-blind. what surface adds is SATELLITE state (.desktop, default-app,
  icon, a unit) — each ALREADY a companion resource the bundle composes (`DeclaredUnixFile`,
  `DeclaredUnixDefaultApp`, `DeclaredUnixSystemdUnit`), never a property of the install. a split on
  surface would cut the resource on state that is not on it — the wrong cut. this is why every
  surface-word (`Tool`/`Command`/`Application`) is ruled out as the family noun.
- **`managed?` is not orthogonal** — it derives from via (unmanaged = the binary arm); it is the
  reason the binary arm carries checksum + version-parse.

### part 3 — the resources of one (the singleton tail)

a "resource of one" = a resource type with exactly ONE instance across the whole forest. the
earlier thread asked whether these are worth modeling. the honest split:

**singleton INSTANCE of a generic type — cheap, no new type.** `1.2.power` (two conf files),
`5.3.brains` settings.json, `6.2.codium` product.json — each is one-of-a-kind in the forest, but it
is just a `DeclaredUnixFile` with one instance. no bespoke type is owed. these are singletons only by
accident of there being one browser, one prompt config.

**singleton that needs a BESPOKE type — the real tail (verified against read bodies).** here the
resource is one AND its `get`/`set` cannot be borrowed from a generic:

| resource | why it needs its own type | where the bespoke logic lives |
|----------|---------------------------|-------------------------------|
| `DeclaredUnixSwapfile` | desired state is DERIVED (2×ram capped at ½ disk) and CONDITIONAL (defer if the image owns a hibernation resume target) | inside `getUnixSwapfile` (resume_offset) + a `computeDesiredSwapfile` transformer |
| `DeclaredUnixSshKeypair` | ⚠️ **ALREADY BUILT — reuse `declastruct-unix-network`, do not re-author** | see the reuse note below |
| `DeclaredUnixUserGroup` | membership, not a file; `set` = `groupadd -f` + `usermod -aG`; takes effect only on a NEW login (a claim the verify can only partly prove — an exit-3 shape) | inside `setUnixUserGroup` |

**`SshKeypair` is DONE, in `declastruct-unix-network` (verified 2026-08-02).**
`src/domain.objects/DeclaredUnixSshKeypair.ts` + `src/access/daos/DeclaredUnixSshKeypairDao.ts` already
implement it, and they validate this dream's whole model independently:
- `unique = ['via', 'uri']` — natural key on the private-key path (`via: 'ssh-keygen'` — the same
  `Via$Mechanism` grammar this dream settled on).
- `readonly = ['publicKey']` — the derived-on-mint `.pub`, stripped from the compare by the SAME
  `omitReadonly` the core uses. INDEPENDENT proof the escape-hatch's `readonly` trick is how this
  ecosystem already keeps derived/injected fields out of the plan diff.
- **never-clobber is `upsert: null`, NOT a bespoke guard** (my earlier "inside setUnixSshKeypair"
  was wrong). the DAO sets `set.upsert = null` → findsert-only → a present private key is never
  overwritten, expressed in the DAO SHAPE, not in imperative set-logic. `delete` is wired
  (`delUnixSshKeypair`), and the verbs are `getOne`/`set`/`del` per canon.

so `SshKeypair` leaves this dream's "owed" list entirely — it is a REUSE, not a build.
`declastruct-unix-network` is the live precedent for how a `declastruct-unix` resource is authored
(dobj + DAO + `getOne`/`set`/`del` operations + osUnix* sdks), and the **stated plan is to pull
`-network` INTO `-unix` proper eventually** — so `-unix` should depend on / absorb it, and follow its
patterns for each named type still owed below (Swapfile, UserGroup).

and one C-ISH that mostly composes generics:

| resource | why not fully bespoke | composes |
|----------|-----------------------|----------|
| `DeclaredUnixLoginShell` | `get` = `getent passwd`, `set` = `chsh -s` — both generic keyed ops. only the pam-refused FALLBACK is special | a `FileBlock` (`~/.bash_profile` `exec zsh`) where chsh is refused |

the count, updated: of 43 leaves, the bespoke-type singletons are **2 still-owed** (`Swapfile`,
`UserGroup`) + **1 already-built** (`SshKeypair`, in `-network`) + 1 C-ish (`LoginShell`). the read
SHRANK this tail from the inferred ~5: `Credential` split (ssh → `SshKeypair`, gh → `ConfigViaGh`
generic), `Terminfo` DISSOLVED (its provision is literally `pkg_install kitty-terminfo` — a data-only
`PackageViaApt`, not a bespoke type; the `tic`-compiled fallback I'd cited was DELETED code whose
header comment I misread as live), and `DefaultApp`/`FontFile` left the tail entirely (→
`Config`/`Package`/`Font`). so the
"long tail" the earlier thread worried about is SHORT — and one of its members is already written.
it is exactly the tail that carries the derived/conditional/secret logic a generic `set({ upsert })`
relocates into a fat `get`/`set` rather than eliminates. declastruct buys structural idempotency + an
honest plan-diff for ALL 43; the bespoke owed-list is now just Swapfile + UserGroup.

### the read is the whole game

scan the `get` column of part 2: it is a different probe per type, and the tier-B/C reads
(`infocmp`, a `--version` parse, `resume_offset`, a live credential probe) are the ones that make
`plan` honest AND the ones that are real work to write. today's `--mode plan` lists intentions
precisely because these reads do not yet exist. porting them IS the project — the `set` side is
mostly the bash upsert bodies you already have, restructured.

### the one that pays first

`DeclaredUnixFileLine` (2 instances today: the tty erase byte, the ~/.profile PATH hook) is the one
that pays for itself immediately: the unguarded-`>>` defect is the single most-repeated hazard the
idempotency rule warns about, and a resource with `path + line` as its unique key cannot commit it.

## .the seams that make this hard, named honestly

1. **the order axis.** `install_robot_brains` needs `install_node` first. declastruct needs a
   dependency edge, or the resource set needs a topological drive. the bash inventory gets this
   for free by virtue of a list — that is the one merit a list has.
2. **`--for local|cloud`.** today a tag on a `step` line. as declared resources it is a
   predicate over the set. probably fine, and probably better.
3. **the bootstrap floor.** `grove.bootstrap.sh` must still be plain bash — a declastruct
   driver needs node, and node is one of the items it installs. so bash does not go away; it
   shrinks to the floor. that boundary is already recorded as the one exemption in
   `rule.require.root-install-invocation`.
4. **read is harder than write on a box.** `get` for `DeclaredUnixPackageViaApt` is `dpkg -s`; for
   `DeclaredUnixFileLine` it is a grep; for `DeclaredUnixBinary` it is a `--version` parse per tool.
   the reads are where the real work is, and they are also exactly what makes `plan` honest.
5. **the local/remote axis.** a provider that runs ON the box vs one that drives it over ssh.
   the `duct`/`grove` layer already solves reach, so the provider should probably assume it runs
   locally and let `grove.send` place it.

## .what would prove it

do not port 43 leaves. port **one probe per tier**, so the spike tests the read at each level of
difficulty — because the `get` is the whole game (part 2):

- **tier A** — `DeclaredUnixFileLine` (the stacked-append hazard; the one that pays first). proves
  the cheap grep-shaped read and the `path + line` key that cannot commit the unguarded-`>>` defect.
- **tier A/B, the family** — `DeclaredUnixPackageViaApt` (with a declared `repo`, e.g. docker or gh).
  proves the manager read (`dpkg -s`) AND that `via.apt.repo` folds the old apt-repo concern in.
- **tier C** — `DeclaredUnixSwapfile` (the hardest bespoke read: `resume_offset` + fstab + a
  `computeDesiredSwapfile` transformer). proves the derived/conditional singleton the generic
  `set({ upsert })` cannot subsume.

then run `plan` twice on a converged grove and confirm it reports **no change** — which is a
claim today's `--mode plan` cannot make at all, because it lists intentions rather than deltas.

## .how it gets tested — a demo EC2 grove, reached over ssh

the integration and acceptance tests APPLY these resources against a real box and read back the
result. that box is a **demo EC2 instance, reached over ssh** — not a mock, not a local container.
this closes the loop `rule.forbid.integration.mocks` / `rule.forbid.acceptance.mocks` demand: a
`UnixPackageViaApt` is only proven when a real `dpkg -s` on a real debian says so.

the test fixture provisions itself with **`declastruct-aws`, which already exists** — so the whole
lifecycle is declastruct end to end:

- **arrange** — `declastruct-aws` declares the demo EC2 instance (+ its vpc/sg/key) and `set`s it up.
  a fresh debian cloud image is exactly the blank box these resources are written for (it ships no
  swap, no flatpak, no node — the conditions half the leaves exist to handle).
- **act** — `declastruct-unix` executes **ON that box** and applies its resources locally. it is an
  "apply on THIS machine" request, exactly like a `grove.provision` run today. the SSH is only the
  TRANSPORT that reaches the box to kick the run off — and that reach already works fine, solved by
  the `duct`/`grove` layer (`grove.send`). the demo box IS a grove in every sense — a headless
  `cloud@aws.ec2` server — so the `--for cloud` predicate and every `🌙 declined` leaf get real
  coverage a local laptop cannot give.
- **assert** — read the box back: `get` returns the converged state, and a second `plan` reports
  **no change** (the idempotency + honest-diff claim). the acceptance test is the plan-apply-apply
  proof this repo already runs for bundles (`howto.prove-bundles-plan-apply-apply`), now against a
  declared resource set.
- **teardown** — `declastruct-aws` `del`s the instance, so no cost lingers and each run starts blank.

this is the symbiosis the two providers were built for: `declastruct-aws` makes the CANVAS (the box),
`declastruct-unix` PAINTS it (the tree, executed on the box), and both speak the same `get`/`set`
contract — so the test harness is itself two declastruct plans, not a pile of bespoke fixture bash.

⚠️ **`declastruct-unix` does NOT need ssh support of its own** — this SETTLES seam #5 (below) in
favor of its "assume local" lean, it does not overturn it. the provider's `get`/`set` execute against
the LOCAL box; a `dpkg -s` is a `dpkg -s`, not an `ssh box dpkg -s`. to reach the box is a separate,
already-solved concern (the duct). so the provider stays a plain "apply on this machine" request, and
the ssh transport is external to it — the same boundary the bash driver already keeps (the driver
executes on the box; `grove.send` places it there).

one honest note — **credentials on the demo box.** the `SshKeypair`, `ConfigViaGh`, and
`ConfigViaGitconfig` resources need real secrets to converge on the demo box — the same
`plan.grove-credentials.md` gap the bash leaves already flag. the acceptance test either injects a
scoped `GH_TOKEN` (never a login) or asserts the `🌙 declined` path, per `rule.require.failfast` for
absent creds.
