# 🌙 dream: the mechanic role's `*.uses --org * allow:*` deny rules match on claude 2.1.330

- kind: reseed
- owner: ehmpathy/rhachet-roles-ehmpathy (role=mechanic)
- caught 2026-11-23

## .the cue that fired

`rhx brains.claude.enroll.trial --which latest` (claude-code 2.1.330) printed, at clone start
(verbatim cli text):

```
Permission deny rule (.../settings.of.repo.json): Bash(rhx git.commit.uses --org * allow:*)
mixes * with the trailing :* prefix syntax, so it is matched as a literal prefix (the * is
not expanded) and will likely never match. Use Bash(rhx git.commit.uses --org * allow*)
```

the pinned 2.1.280 printed no such notice on the same actor.

## .the gap, precisely

8 deny rules, generated from the mechanic role into every actor's `settings.of.repo.json`:

- `Bash(rhx git.{commit,branch}.uses --org * {allow,del}:*)`
- `Bash(npx rhachet run --skill git.{commit,branch}.uses --org * {allow,del}:*)`

their job: a clone may not grant itself commit/branch quota for an org. on 2.1.330 the cli
states they never match. on 2.1.280 they most likely never applied either: the 2.1.282
release notes read "Fixed Bash permission rules with a mid-pattern `:*` being skipped in
settings files while `--allowedTools` honored them; they now work from every source, with a
startup warning on how they match". so the gap predates the bump; 2.1.330 only names it.
📌 the "skipped on 2.1.280" read rests on that note, not a probe.

also flagged, on both versions: `Write(.route/**)` in allow is ignored by file checks; the cli
asks for `Edit(.route/**)`.

## .the shape of the fix

in the mechanic role's settings source: `allow:*` → `allow*`, `del:*` → `del*`; and
`Write(.route/**)` → `Edit(.route/**)`. then a clamp: an enrolled clone on 2.1.330 starts
with zero `Permission deny rule` / `Permission allow rule` notices.

## .why it is not done in this round

the rules are another repo's generated output; an edit here is overwritten by the next hook
sync. it belongs upstream, via radio.
